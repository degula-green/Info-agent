# 实体定位五层管线接口草案

> 状态：讨论稿
> 关联文档：树形RAG设计方案.md、实体节点生成方案-MVP.md、interfaces/07-rag-admin-entity-tree-api.md

## 1. 范围与前提

本文只定义**查询侧实体定位**（原设计 Layer 1）的接口契约，不涉及节点内 chunk 检索与关系扩展的内部实现，只规定其入参形状。

已确认的前提：

1. 采用新设计（树 + 图混合），树只负责定位与归属，关系网络负责横向扩展。
2. 本期 domain 固定 5 类：`organization` / `person` / `project` / `policy` / `contract`。
3. 数据库表在现有表上原地改造，不兼容旧逻辑。
4. 实体向量存 PostgreSQL（远端已有 pgvector 扩展），不再走应用层余弦，也不放 ES。
5. 定位粒度为 **mention**，不是整条 query。多实体查询是常态，禁止首层命中即全局返回。

## 2. 总体流程

```text
query
  │
  ├─ L0  mention 抽取（可能得到 0..N 个 mention）
  │
  └─ 对每个 mention 独立执行：
       L1 精确匹配 ──命中──┐
       L2 模糊匹配 ──命中──┤
       L3 语义匹配 ──命中──┤
       L4 LLM 门控验证 ────┤
                           └─ 得到该 mention 的候选集
                              │
     ┌────────────────────────┘
     ▼
  L5 汇总与降级
     - 范围合成（多实体 AND / OR）
     - 残查询改写（剥离实体名）
     - 无实体 → 传统全库检索
     - 实体命中但 chunk 不足 → 关系扩展
```

关键约束：

- **L1/L2/L4 的作用域是单个 mention**，返回的是“这个 mention 指哪个实体”的判定，不是整条 query 的最终结果。
- **L1 命中不阻断其他 mention 的解析**，也不阻断同一 mention 的多候选。
- 每一层的置信度口径不同，**禁止跨层加权求和**，下游按 `match_method` + 分层阈值门控。

## 3. 数据结构定义

### 3.1 EntityMention（L0 产物）

```python
@dataclass(frozen=True)
class EntityMention:
    mention_id: str            # 管线内序号，如 "m0"
    surface_form: str          # 原文中的说法，如 "A项目"
    normalized_form: str       # normalized_text 之后
    start: int | None          # 在 query 中的字符偏移，用于残查询改写
    end: int | None
    type_hint: str | None      # 查询中显式出现的类型词推断，如 "项目"
    is_deictic: bool = False   # 指代表达："那个项目"、"上次说的"
    source: str = "query"      # query | conversation
```

### 3.2 EntityCandidate（逐层匹配产物）

```python
@dataclass(frozen=True)
class EntityCandidate:
    entity_id: str
    domain: str                # 5 类之一
    canonical_name: str
    match_method: str          # exact | alias | fuzzy | semantic | llm_context
    match_score: float         # 本层口径下的置信度，见第 5 节
    evidence: dict             # 命中的别名、trgm 相似度、向量距离、LLM 理由
    registry_version: int      # 用于缓存失效与诊断
```

### 3.3 LocatedEntity（mention 的最终判定）

```python
@dataclass(frozen=True)
class LocatedEntity:
    mention_id: str
    entity_id: str
    domain: str
    canonical_name: str
    match_method: str
    match_score: float
    verified: bool             # 是否经过 L4 验证
```

### 3.4 EntityScope（汇总产物，交给 chunk 检索）

```python
@dataclass(frozen=True)
class EntityScope:
    entity_ids: tuple[str, ...]
    composition: str           # and | or
    min_mount_confidence: float
    residual_query: str        # 剥离实体名后的检索语句
    unresolved: tuple[str, ...]  # 未能定位的 mention 原文
```

## 4. 逐层接口

每层统一给出：输入、处理规则、输出、置信度、失败处理、落库/查询字段、延迟预算。

### L0 mention 抽取

**输入**：`query`、`scope_type`、`scope_id`、`registry_version`（可选，用于缓存）。

**处理**：

1. 在 query 中扫描已注册实体的 `canonical_name` / `normalized_key` / alias，做最长优先、互不重叠的切分。复用现有 `EntityMatcher` 的思路，但产出的是 mention 位置而不是最终实体。
2. 对未被第 1 步覆盖的片段，按类型后缀词（公司/项目/系统/政策/合同/协议等）做轻量候选抽取，`type_hint` 取后缀对应类型。
3. 识别指代表达（那个/这个/上次说的/刚才提到的），产出 `is_deictic=True` 的 mention，`surface_form` 保留原文。

**输出**：`list[EntityMention]`，允许为空。

**失败处理**：抽不到 mention 直接进 L5 的全库降级。

**落库/查询字段**：无（纯内存，依赖第 6 节的实体索引缓存）。

**延迟预算**：p95 ≤ 3ms（命中缓存时 ≤ 1ms）。

### L1 精确匹配

**输入**：单个 `EntityMention`、`scope_type` / `scope_id`。

**处理**：

```sql
-- 允许返回多条：同一名称可以同时存在于不同 domain
SELECT e.id, e.domain, e.canonical_name, e.registry_version, 'exact' AS method
FROM entities e
WHERE e.scope_type = %(scope_type)s
  AND e.scope_id = %(scope_id)s::uuid
  AND e.status = 'active'
  AND e.normalized_key = %(normalized)s
UNION
SELECT e.id, e.domain, e.canonical_name, e.registry_version, 'alias' AS method
FROM entity_aliases a
JOIN entities e ON e.id = a.entity_id
WHERE a.scope_type = %(scope_type)s
  AND a.scope_id = %(scope_id)s::uuid
  AND a.status = 'active'
  AND a.normalized_alias = %(normalized)s;
```

规则：

- **不加 `LIMIT 1`**，`(scope, domain, normalized_key)` 是联合唯一键，同名跨 domain 合法。
- 不按 domain 过滤；`type_hint` 只用于排序，不作为过滤条件。
- 命中即返回该 mention 的候选集，无需进入 L2/L3。

**输出**：`list[EntityCandidate]`，`match_method` 为 `exact` 或 `alias`。

**失败处理**：空则进入 L2。

**落库/查询字段**：`entities.normalized_key`、`entity_aliases.normalized_alias` 上的唯一索引；配合第 6 节的内存缓存，避免每查询打库。

**延迟预算**：缓存命中 p95 ≤ 1ms，回源 ≤ 5ms。

### L2 模糊匹配

**输入**：L1 未命中的 `EntityMention`。

**处理**：三条并列规则，命中任一即产出候选，**不做 AND 组合**。

| 规则 | 条件 | 置信度 | 是否直接采信 |
|---|---|---|---|
| 三元组相似度 | `similarity(name, mention) >= 0.8` | `0.80 ~ 0.85`（按相似度线性映射） | 是 |
| 编辑距离 | 归一化编辑距离 `>= 0.8`，仅用于长度 ≤ 12 的短名 | `0.80` | 是 |
| 包含/前缀 | mention 是 `canonical_name` 的真子串且长度 ≥ 2 | `0.70` | 否，必须进 L3/L4 验证 |

说明：

- pg_trgm 对中文短名与缩写（`aims` → `AIMS系统开发项目`）相似度很低，L2 的实际定位是**错别字容忍**，不是简称识别。简称靠 L3。
- 包含/前缀规则专门处理“青云” → “青云飞鹏官网项目”这类省略，但容易误伤，不给直接采信资格。

**输出**：`list[EntityCandidate]`，`match_method = fuzzy`。

**失败处理**：空则进入 L3。

**落库/查询字段**：`entities.canonical_name`、`entities.normalized_key`、`entity_aliases.normalized_alias` 上的 `gin_trgm_ops` 索引。

**延迟预算**：p95 ≤ 10ms。

### L3 语义匹配（pgvector ANN）

**输入**：L1/L2 未产出“可直接采信候选”的 `EntityMention`。

**硬过滤（只允许 scope 作为硬条件）**：

```sql
WHERE e.scope_type = %(scope_type)s
  AND e.scope_id = %(scope_id)s::uuid
  AND e.status = 'active'
  AND e.embedding IS NOT NULL
```

**软信号（只影响排序，不做过滤）**：

| 信号 | 处理 |
|---|---|
| `type_hint` 与 `domain` 一致 | 距离加权，如 `distance * 0.9` |
| `last_mentioned_at` 在近 3 个月内 | 距离加权，如 `distance * 0.95` |
| `keywords` 命中 mention | 距离加权，如 `distance * 0.97` |

**查询**：

```sql
SELECT e.id, e.domain, e.canonical_name,
       1 - (e.embedding <=> %(query_vector)s::vector) AS score
FROM entities e
WHERE e.scope_type = %(scope_type)s
  AND e.scope_id = %(scope_id)s::uuid
  AND e.status = 'active'
  AND e.embedding IS NOT NULL
ORDER BY e.embedding <=> %(query_vector)s::vector
LIMIT %(over_fetch)s;   -- 建议 50，应用层收敛到 10
```

规则：

- 使用 HNSW 索引（`vector_cosine_ops`），不用 IVFFlat：实体持续新增，且 IVFFlat 建索引需要训练数据与 `lists` 调参。
- 带 WHERE 过滤的 ANN 存在后过滤召回不足问题，**必须 over-fetch**（如 50 → 10），或启用 pgvector 0.8 的 `hnsw.iterative_scan`。
- 保留阈值：`score >= 0.75` 才进入候选集，否则丢弃。
- `embedding IS NULL` 的实体不参与，但不得因此报错；新建实体在向量回填完成前只能靠 L1/L2 命中。

**输出**：`list[EntityCandidate]`，`match_method = semantic`，`evidence` 记录原始距离与加权后距离。

**失败处理**：空或全部低于阈值则进入 L5（或对指代 mention 进入 L4）。

**落库/查询字段**：`entities.embedding vector(1536)`、`embedding_model`、`embedding_dimensions`、`embedding_status`、`embedding_updated_at`、`keywords`、`last_mentioned_at`。

**延迟预算**：p95 ≤ 30ms（含 embed 调用则在 50ms 量级）。

### L4 LLM 门控验证

**触发条件（满足任一才调用，否则跳过）**：

- L2 的 `fuzzy/包含` 候选或 L3 候选存在，且 `top1_score < 0.85`；
- `top1_score - top2_score < 0.08`（多候选难以区分）；
- mention 为指代表达 `is_deictic=True`；
- 同一 query 内有多个 mention 且候选集合重叠。

L1 的单一 exact/alias 命中**不调用** L4。

**输入**：

```python
@dataclass(frozen=True)
class LLMVerifyRequest:
    mention: EntityMention
    candidates: tuple[EntityCandidate, ...]   # 只含实体 ID、名称、domain、别名、简述
    context_messages: tuple[str, ...]         # 最近 ≤ 10 条对话消息
    allow_none: bool = True
```

**输出**：

```python
@dataclass(frozen=True)
class LLMVerifyResult:
    entity_id: str | None     # 必须属于入参候选集，否则丢弃
    confidence: float
    reason: str
    degraded: bool = False    # 超时或异常导致的降级
```

规则：

- LLM 只能从给定候选中选择，允许返回“都不是”。
- 返回后**必须校验** `entity_id ∈ candidates`，防止编造。
- `confidence > 0.7` 才采信；否则按 L3 的 top1 处理。
- 超时硬上限建议 800ms；超时按 `degraded=True` 处理，回落到 `top1_score >= 0.85` 的候选，否则丢弃该 mention。
- 结果按 `(mention normalized, 候选集 hash, 对话窗口 hash)` 缓存。

**上下文来源（待定接口项）**：RAG 服务当前 `SearchRequest` 只有 `conversation_id`，拿不到消息正文。两种方案：由 Agent 在请求里直接传 `context_messages`；或 RAG 回查 knowledge 服务。**建议由 Agent 传入**，避免 RAG 增加跨服务依赖。

**落库/查询字段**：无持久化；建议在检索诊断中记录 `llm_invoked / llm_reason / degraded`。

**延迟预算**：未触发时为 0；触发时 p95 400~800ms，必须计入端到端预算并单独监控调用率。

### L5 汇总与降级

**输入**：所有 mention 的 `LocatedEntity` 集合 + 未能定位的 mention。

**处理**：

1. **范围合成**：
   - 查询语义为“同一实体的约束”时用 AND，如“张三在A项目的记录”；
   - 查询语义为“并列列举”时用 OR，如“A项目或B项目的进展”；
   - 无法判定时**默认 AND**（更保守，噪音更低），并在诊断中标记。
2. **残查询改写**：把命中的 mention 从 query 中剥离，剩余部分作为 `residual_query` 交给节点内检索，避免实体名主导 BM25。
3. **降级分支**：
   - 全部 mention 未定位 → 传统全库检索，`fallback_reason = no_entity_match`；
   - 已定位但节点内 chunk 数量低于阈值（如 `top_k * 0.5`）→ 先做 1 跳关系扩展，仍不足再全库兜底。

**输出**：`EntityScope` + 定位诊断。

**失败处理**：任何一层异常都不得让检索失败，必须回落到传统全库检索。

## 5. 置信度口径总表

| match_method | 分数区间 | 含义 | 是否可直接采信 | 说明 |
|---|---|---|---|---|
| `exact` | 0.95 | canonical_name 规范化后完全一致 | 是 | 同一名称跨 domain 时返回多条 |
| `alias` | 0.93 | 命中已审核别名 | 是 | |
| `fuzzy`（trgm/编辑距离） | 0.80 ~ 0.85 | 字符串近似，容忍错别字 | 是（≥0.8） | 不解决缩写 |
| `fuzzy`（包含/前缀） | 0.70 | mention 是名称真子串 | 否 | 必须经 L3/L4 验证 |
| `semantic` | 0.75 ~ 0.90 | 向量余弦，已按软信号加权 | 仅 `>=0.85` 且 top1/top2 差距足够 | |
| `llm_context` | 0.70 ~ 0.95 | LLM 在候选集内消歧 | 是（>0.7） | 必须校验 ID 属于候选集 |

**强制约束**：

- 上述分数**不可跨方法比较或相加**，下游只按 `match_method` + 各自阈值门控。
- 每个 `LocatedEntity` 必须携带 `match_method`，诊断与评估按方法分别统计，不合并成一个“准确率”。

## 6. 实体索引缓存

为让 L1 真正达到毫秒级，避免每次查询回源数据库：

```python
@dataclass
class EntityLocatorCache:
    scope_key: str
    registry_version: int
    exact_index: dict[str, tuple[EntityCandidate, ...]]  # normalized -> candidates
    alias_index: dict[str, tuple[EntityCandidate, ...]]
```

失效键为 `(scope_key, registry_version)`，与现有 `entity_registry.registry_version` 递增机制一致。审核 `promote/merge` 后 `registry_version` 自增，缓存自然失效，无需额外通知。向量不进入缓存，L3 直接查库（pgvector 在远端）。

索引：

```sql
CREATE INDEX entities_embedding_hnsw_idx ON entities
    USING hnsw (embedding vector_cosine_ops);
CREATE INDEX entities_name_trgm_idx ON entities
    USING gin (canonical_name gin_trgm_ops);
CREATE INDEX entities_normalized_trgm_idx ON entities
    USING gin (normalized_key gin_trgm_ops);
CREATE INDEX entities_keywords_gin_idx ON entities USING gin (keywords);
```

实体向量生成是外部 embedding 调用，**异步回填**：建实体时先写行、`embedding_status='pending'`，由任务回填；L3 必须容忍 `embedding IS NULL`。

| 字段 | 类型 | 说明 |

### 7.4 其余表

- `entity_aliases`：保留，`domain` CHECK 收窄 5 类。
- `entity_candidates` / `entity_candidate_mentions`：保留，`candidate_domain` 收窄 5 类，生成来源由正则改为 LLM 窗口扫描。
- `entity_review_requests`：保留不变。
- `tree_nodes`：**删除**，管理端树由 `entities GROUP BY domain` 派生。
- `branch_refresh_jobs`：保留，语义改为“重刷 mount 并回写 ES”。

## 8. 查询字段（Elasticsearch）

chunk 文档新增两个字段，替代 `branch_keys` 作为过滤契约：

```json
{
  "entity_ids": ["uuid-1", "uuid-2"],
  "entity_mounts": [
    {"entity_id": "uuid-1", "domain": "project", "confidence": 0.95, "method": "explicit"},
    {"entity_id": "uuid-2", "domain": "person", "confidence": 0.80, "method": "window_batch"}
  ]
}
```

映射：

```json
"entity_ids": {"type": "keyword"},
"entity_mounts": {
  "type": "nested",
  "properties": {
    "entity_id": {"type": "keyword"},
    "domain": {"type": "keyword"},
    "confidence": {"type": "float"},
    "method": {"type": "keyword"}
  }
}
```

查询形状：

```json
{
  "bool": {
    "filter": [
      {"terms": {"entity_ids": ["uuid-1", "uuid-2"]}},
      {"nested": {
        "path": "entity_mounts",
        "query": {"bool": {"must": [
          {"terms": {"entity_mounts.entity_id": ["uuid-1", "uuid-2"]}},
          {"range": {"entity_mounts.confidence": {"gte": 0.85}}}
        ]}}
      }}
    ]
  }
}
```

说明：

- `entity_ids` 做廉价 terms 预过滤；严格场景（表单填写等）再叠加 `entity_mounts.confidence` 的 nested 条件。
- 不用 PG 回传 chunk_id 列表，也不用 `branch_key` 前缀过滤。
- 新增字段属于 mapping 增量变更，不需要重建索引；由 mount 刷新通道回写存量文档。

## 10. 延迟预算

| 层 | 未触发 | 触发 |
|---|---|---|
| L0 | ≤ 3ms | ≤ 3ms |
| L1 | ≤ 1ms（缓存） | ≤ 5ms |
| L2 | - | ≤ 10ms |
| L3 | ≤ 30ms | ≤ 50ms（含 embed） |
| L4 | 0 | 400 ~ 800ms |
| L5 | ≤ 5ms | ≤ 5ms |

- 常规路径（L1 或 L3 直接命中，L4 跳过）：p95 ≤ 80ms。
- 升级路径（触发 L4）：p95 会到 500ms 量级，必须单独统计 **L4 调用率**，目标控制在语义查询的 20% 以内。
- 端到端 p95 < 150ms 的目标只在“L4 未触发”前提下成立，需在验收指标里拆开写。
