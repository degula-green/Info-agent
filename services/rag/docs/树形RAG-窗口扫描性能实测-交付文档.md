# 树形RAG 窗口扫描性能实测 - 交付文档

- **对应计划项**: 实施计划 Phase 2「上量前必须补测」三项
- **分支**: `codex/tree-rag-v2`
- **实测日期**: 2026-10-10
- **状态**: 延迟与吞吐已量测；**发现一个严重缺陷并已修复**；另一个稳定性问题尚无解法

## 1. 方法与复现

```bash
python scripts/measure_window_scan.py \
    --conversation-limit 4 --windows-per-conversation 4 --concurrency 1,8,16
```

脚本使用**库内真实消息**构造 20 条窗口，走与 worker 完全相同的 prompt 构造与
抽取客户端，只调用模型、不写数据库。已知实体用内存中的合成集合填充——真实 worker
会把 scope 内 active 实体写进 prompt，空注册表会低估 prompt 体积，而写测试行进库
又会污染数据。

## 2. 延迟与吞吐

12 个真实 20 条消息窗口，prompt 2417~4356 字符：

| 并发 | 总耗时 | p50 | p95 | token/次 | tokens/min |
|---|---|---|---|---|---|
| 1 | 76.6s | 6418ms | 7042ms | 1703 | 16,002 |
| 8 | 13.4s | 6569ms | 7375ms | 1702 | 91,320 |
| 16 | 7.2s | 6445ms | 7210ms | 1703 | 169,827 |

结论：

- **单次约 6.5 秒**（p50 6.4~6.6s，p95 7.0~7.4s）。这比早先在 2 条消息小窗口上
  测出的 1.7s 高得多——prompt 从约 250 token 涨到约 1700 token，prefill 是主要成本。
  之前按小窗口推算的延迟是错的，以本表为准。
- **并发到 16 没有排队**：p50 在三档并发下几乎不变（6.4→6.6s），说明瓶颈不在 provider
  侧，可以放心按 8~16 配置。
- **TPM 随并发近似线性**：16k → 91k → 170k。按 600 会话/小时（约 800 窗口、
  约 136 万 token/小时 ≈ 2.3 万 token/min）计算，16 并发有 7 倍余量。

## 3. 发现一：已知实体列表让模型返回空（已修复）

### 现象

同一窗口，只改 prompt 里"已知实体"列表的长度：

| 已知实体数 | 抽出实体 | completion tokens |
|---|---|---|
| 0 | 3 | 219 |
| 1 | 3 | 163 |
| 3 | 3 | 214 |
| **10** | **0** | **9** |
| **20** | **0** | **9** |

重复 4 次的对照：

```text
known= 0: [3, 3, 3, 3]
known=20: [3, 0, 0, 0]
```

而 worker 的 `known_entity_limit` 默认是 **40**。也就是说：**注册表一旦超过约 10 个
实体，窗口扫描就会基本返回空，整条挂载链路静默失效**——不报错、不告警，只是树不再
增长。这正是"上量前必须补测"要拦的问题。

### 原因

原 prompt 的措辞是"## 已知实体（如果对话提到，告诉我是哪个已知实体）"，把任务
框定成了"在已知列表里匹配"。当窗口里的实体都不在列表中时，模型就输出空数组，
忽略了"提取所有实际讨论的实体"这条规则。

### 修复与验证

把该段改为"参考用的已知实体（只用于填写 existing_entity_id，不要因为不在下表就
跳过任何实体）"，并在规则 1、3 中重申"不在表里的实体同样必须提取"。

```text
修复后 known= 0: [3, 3, 3, 3]
修复后 known=20: [3, 3, 3, 3]
修复后 known=40: [3, 3, 3, 3]
```

12/12 全部成功，包括生产上限 40 条。已加单测锁住这段措辞，防止回归。

## 4. 发现二：单窗口抽取结果不稳定（未解决）

同一组 12 个窗口跑三次，得到的三组结果：

```text
并发 1 : per_window_entities = [3,3,0,0,0,4,0,0,3,0,0,0]   合计 13
并发 8 : per_window_entities = [0,3,0,0,0,0,4,3,0,0,0,3]   合计 13
并发 16: per_window_entities = [0,0,0,0,0,0,0,0,3,3,3,4]   合计 13
```

三点值得注意：

1. **每次都是 12 个窗口里 8 个返回空**，合计实体数稳定在 13——聚合层面是可复现的。
2. **但返回空的是哪 8 个，每次都不一样**（只有极少数窗口在两次之间重合）。
3. 因此"某窗口返回空"**不能解释为该窗口没有实体**，而是模型对该窗口这次没抽出来。

### 影响

命中率被 `merge_chunk_mounts` 的幂等语义部分补偿——`window_step=10` 让每条消息
落在约 2 个窗口里。但按每次约 2/3 的窗口空转估算，两个窗口同时失败的比例仍不低，
**挂载召回会明显低于设计预期**。

### 尚未验证的候选解法

```text
- 空结果重试一次：直接针对该现象，但会把每次空窗的调用成本翻倍（而 2/3 的窗口都会空转）
- 换模型或换端点：需要先确认是模型能力问题还是这个代理端点的行为
- 降低窗口内消息数：prompt 从 1700 token 降下来，可能减少注意力稀释
- 把"提取所有实体"与"匹配已知实体"拆成两次调用：信息量更单一，但调用次数翻倍
```

**建议在解决之前不要上量**：当前状态下窗口扫描能产出候选与挂载，但召回率不可信，
而"挂载准确率 > 85%"这条验收标准在召回残缺的情况下没有意义。

## 5. 结论

```text
可以定的:
  - 单窗口延迟约 6.5s，p95 约 7.2s（真实 20 条窗口）
  - 并发 8~16 无排队，TPM 分别约 9 万 / 17 万，远高于需求
  - 配置并发 8 是合理的起点

必须解决:
  - 单窗口抽取不稳定（2/3 空转，且每次空转的窗口随机）——这是上量的硬前提
```
