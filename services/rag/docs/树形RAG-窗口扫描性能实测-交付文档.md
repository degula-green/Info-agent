# 树形RAG 窗口扫描性能实测 - 交付文档

- **对应计划项**: 实施计划 Phase 2「上量前必须补测」三项
- **分支**: `codex/tree-rag-v2`
- **实测日期**: 2026-10-10
- **状态**: 延迟与吞吐已量测；**发现一个严重缺陷并已修复**；另一个稳定性问题尚无解法

## 1. 方法与复现

```bash
python scripts/measure_window_scan.py \
    --conversation-limit 4 --windows-per-conversation 4 --concurrency 1,8,16
```

脚本使用**库内真实消息**构造 20 条窗口，走与 worker 完全相同的 prompt 构造与
抽取客户端，只调用模型、不写数据库。已知实体用内存中的合成集合填充——真实 worker
会把 scope 内 active 实体写进 prompt，空注册表会低估 prompt 体积，而写测试行进库
又会污染数据。

## 2. 延迟与吞吐

12 个真实 20 条消息窗口，prompt 2417~4356 字符：

| 并发 | 总耗时 | p50 | p95 | token/次 | tokens/min |
|---|---|---|---|---|---|
| 1 | 76.6s | 6418ms | 7042ms | 1703 | 16,002 |
| 8 | 13.4s | 6569ms | 7375ms | 1702 | 91,320 |
| 16 | 7.2s | 6445ms | 7210ms | 1703 | 169,827 |

结论：

- **单次约 6.5 秒**（p50 6.4~6.6s，p95 7.0~7.4s）。这比早先在 2 条消息小窗口上
  测出的 1.7s 高得多——prompt 从约 250 token 涨到约 1700 token，prefill 是主要成本。
  之前按小窗口推算的延迟是错的，以本表为准。
- **并发到 16 没有排队**：p50 在三档并发下几乎不变（6.4→6.6s），说明瓶颈不在 provider
  侧，可以放心按 8~16 配置。
- **TPM 随并发近似线性**：16k → 91k → 170k。按 600 会话/小时（约 800 窗口、
  约 136 万 token/小时 ≈ 2.3 万 token/min）计算，16 并发有 7 倍余量。

## 3. 发现一：已知实体列表让模型返回空（已修复）

### 现象

同一窗口，只改 prompt 里"已知实体"列表的长度：

| 已知实体数 | 抽出实体 | completion tokens |
|---|---|---|
| 0 | 3 | 219 |
| 1 | 3 | 163 |
| 3 | 3 | 214 |
| **10** | **0** | **9** |
| **20** | **0** | **9** |

重复 4 次的对照：

```text
known= 0: [3, 3, 3, 3]
known=20: [3, 0, 0, 0]
```

而 worker 的 `known_entity_limit` 默认是 **40**。也就是说：**注册表一旦超过约 10 个
实体，窗口扫描就会基本返回空，整条挂载链路静默失效**——不报错、不告警，只是树不再
增长。这正是"上量前必须补测"要拦的问题。

### 原因

原 prompt 的措辞是"## 已知实体（如果对话提到，告诉我是哪个已知实体）"，把任务
框定成了"在已知列表里匹配"。当窗口里的实体都不在列表中时，模型就输出空数组，
忽略了"提取所有实际讨论的实体"这条规则。

### 修复与验证

把该段改为"参考用的已知实体（只用于填写 existing_entity_id，不要因为不在下表就
跳过任何实体）"，并在规则 1、3 中重申"不在表里的实体同样必须提取"。

```text
修复后 known= 0: [3, 3, 3, 3]
修复后 known=20: [3, 3, 3, 3]
修复后 known=40: [3, 3, 3, 3]
```

12/12 全部成功，包括生产上限 40 条。已加单测锁住这段措辞，防止回归。

## 4. 发现二：单窗口抽取不稳定（已大幅缓解，未根除）

### 现象

同一批窗口重复跑，**每次都有一部分返回空，但空的是哪些每次都不一样**：

```text
带已知实体列表，12 窗 × 3 次:
  并发 1 : [3,3,0,0,0,4,0,0,3,0,0,0]   合计 13
  并发 8 : [0,3,0,0,0,0,4,3,0,0,0,3]   合计 13
  并发 16: [0,0,0,0,0,0,0,0,3,3,3,4]   合计 13
```

合计实体数稳定、但分布随机，说明"某窗口返回空"**不能解释为该窗口没有实体**，
而是模型这次没抽出来。

### 排查过的三条路

| 方案 | 结果 | 结论 |
|---|---|---|
| 空结果重试一次 | 6 次重试只挽回 0 次；另一轮 14 次挽回 1 次 | 不划算，成本翻倍换 7% |
| 换 `deepseek-v4-pro` | 空转率 **87.5%**，比 flash 更差 | 排除 |
| **去掉 prompt 里的已知实体列表** | 空转率 43.75% → **18.75%** | **采用** |

### 为什么敢直接去掉

三条件同时成立：

1. `existing_entity_id` **只出现在 prompt 里，worker 从不读它**——实体解析由
   `find_entities_by_normalized` 按名称在代码里完成。
2. 该列表与稳定性强相关：列表到约 10 条就会让模型整体返回空（见第 3 节）。
3. 去掉后 yield 反而更高：同样 12 个窗口，实体从 13 个涨到 25 个，
   prompt token 从 1703 降到 920。

### 改进后的实测（8 窗 × 4 次）

```text
window 0: [2,2,2,2] always_found
window 1: [3,3,3,3] always_found
window 2: [0,4,0,4] unstable        ← 残留的不稳定窗口
window 3: [3,3,3,2] always_found
window 4: [3,3,3,3] always_found
window 5: [3,3,2,2] always_found
window 6: [3,3,3,3] always_found
window 7: [0,0,0,0] always_empty

first_attempt_empty_rate: 0.1875（原 0.4375）
```

| 配置 | 空转率 | 稳定命中 | 不稳定 | 恒空 |
|---|---|---|---|---|
| 带已知实体列表 | 43.75% | 3/8 | 3/8 | 2/8 |
| **去掉列表（已实施）** | **18.75%** | **6/8** | **1/8** | 1/8 |

### 残留问题

仍有约 1/8 的窗口在多次尝试间摇摆。`window_step=10` 的 50% 重叠让每条消息落在
两个窗口里，能部分补偿，但按 18.75% 的尝试级空转估算，仍有少量消息可能被两个
窗口同时漏掉。

**建议**：先把空转率作为监控指标（每次扫描记 `empty_window_ratio`），上量后看
真实数据里的挂载覆盖率是否可接受；如果覆盖率不足，再考虑"把窗口缩小到 10 条"
或"拆分提取与匹配两次调用"这两条未验证的路径。

## 4.1 修复后的延迟与吞吐

| 并发 | 总耗时 | p50 | p95 | token/次 | tokens/min |
|---|---|---|---|---|---|
| 1 | 78.2s | 6515ms | 6797ms | 920 | 8,467 |
| 8 | 13.8s | 6786ms | 7124ms | 910 | 47,405 |
| 16 | 6.9s | 6780ms | 6908ms | 906 | 94,303 |

**注意**：prompt token 从 1703 降到 920（-46%），但**单次延迟没有变化**（仍在
6.5~6.8s）。说明延迟由与 prompt 长度无关的固定开销主导，不要指望靠缩小 prompt
来降延迟。TPM 相应从 17 万降到 9.4 万（同样并发下更少的 token），仍远高于需求。

## 5. 结论

```text
可以定的:
  - 单窗口延迟约 6.5s，p95 约 7.1s（真实 20 条窗口），且与 prompt 长度无关
  - 并发 8~16 无排队，TPM 约 5 万 / 9.4 万，远高于需求
  - 配置并发 8 是合理的起点
  - prompt 里的已知实体列表已移除：它既无消费者，又是空转率的主要来源

仍需观察:
  - 残留约 19% 的尝试级空转率，且集中在约 1/8 的窗口上
  - 建议先把空转率与挂载覆盖率接入监控，用真实数据判断是否影响验收
```
