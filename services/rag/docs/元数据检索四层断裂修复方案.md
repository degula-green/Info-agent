# 元数据检索字段补齐方案

## 文档状态

- 版本：v1.1
- 状态：已实施
- 优先级：P0
- 范围：只补齐 Knowledge → RAG → ES 的元数据字段，并确保新数据处理后有值
- 非目标：历史数据回填、元数据查询接口、Agent 工具封装
- 最后更新：2026-10-01

## 1. 本次目标

当前聊天消息和聊天附件的 RAG Chunk 缺少以下可用元数据：

- 发送人身份
- 发送人显示名称
- 发送平台
- 来源群聊名称
- 来源会话平台
- 附件所属消息 ID
- 消息发送时间

本次修改只解决数据链路问题：

```text
Knowledge 业务表
-> knowledge.ready 事件
-> RAG ResourceContext
-> RAG Chunk.context_header
-> Elasticsearch 字段
```

完成后，所有新产生的聊天消息和聊天附件 Chunk 都应携带上述字段。

## 2. 明确不做

本方案不包含以下内容：

1. 不回填历史 Chunk。
2. 不重新触发历史 `knowledge.ready` 事件。
3. 不修改 `/search/global`、`/search/knowledge`、`/search/tree` 的请求协议。
4. 不增加 `sender_names`、`conversation_names` 等查询过滤器。
5. 不增加 `/search/sources`、`/search/content` 等新接口。
6. 不封装 Agent Tool。
7. 不修改前端。

旧数据在补齐前仍可能缺少 sender 和 conversation name 字段，这是本次明确接受的限制。

## 3. 当前代码事实

### 3.1 函数名

实际函数为：

```go
func (s *PostgresStore) TryMarkKnowledgeReady(
    ctx context.Context,
    id string,
    traceID string,
) (bool, error)
```

位置：

`services/knowledge/internal/repository/postgres.go`

不是原方案中写的 `MarkKnowledgeItemReady`。

### 3.2 群聊数据表

当前没有 `knowledge.conversations` 表。

群聊名称、平台和外部会话 ID 来自：

```text
knowledge.conversation_ingestions
```

关键字段：

- `id`
- `name`
- `platform`
- `external_conversation_id`
- `conversation_type`

### 3.3 消息发送人

`knowledge.messages` 当前有：

- `sender_identity_id`
- `sender_display_name`
- `sent_at`
- `message_type`

`knowledge.messages` 没有 `sender_platform`。

发送平台统一从：

```text
knowledge.conversation_ingestions.platform
```

获取。

### 3.4 附件发送人

`knowledge.attachments` 没有 sender 字段。

附件发送人和发送时间必须经过：

```text
attachments.message_id
-> messages.sender_identity_id
-> messages.sender_display_name
-> messages.sent_at
```

获取。

### 3.5 RAG 现状

`ResourceContext` 已有字段：

- `sender_identity_id`
- `sender_display_name`
- `sender_platform`
- `source_conversation_id`
- `source_conversation_type`

尚缺字段：

- `source_conversation_name`
- `source_platform`

`Chunk.create()` 当前只写入以下 `context_header`：

```python
{
    "title": title,
    "file_name": file_name,
    "heading_path": list(heading_path),
    "source_kind": context.resource_type,
}
```

因此即使事件带了 sender，当前也不会写入 ES。

## 4. 字段契约

### 4.1 `knowledge.ready` 新增字段

对聊天消息和聊天附件新增：

```json
{
  "source_message_id": "消息 UUID",
  "sender_identity_id": "发送人身份 UUID",
  "sender_display_name": "张三",
  "sender_platform": "feishu",
  "sent_at": "2026-10-01T10:30:00+08:00",
  "source_conversation_name": "财务项目群",
  "source_platform": "feishu",
  "external_conversation_id": "外部群 ID"
}
```

字段语义：

| 字段 | 含义 | 来源 |
|---|---|---|
| `source_message_id` | 附件所属消息或消息自身 ID | `ki.source_message_id`，附件兜底 `a.message_id` |
| `sender_identity_id` | 发送人身份 ID | `messages.sender_identity_id` |
| `sender_display_name` | 发送人名称 | 消息名称，兜底外部身份名称 |
| `sender_platform` | 发送平台 | `conversation_ingestions.platform` |
| `sent_at` | 消息发送时间 | `messages.sent_at` |
| `source_conversation_name` | 群聊或私聊名称 | `conversation_ingestions.name` |
| `source_platform` | 群聊、私聊所属平台 | `conversation_ingestions.platform` |
| `external_conversation_id` | 第三方平台会话 ID | `conversation_ingestions.external_conversation_id` |

### 4.2 空值规则

聊天消息：

- 上述字段必须全部有值。

聊天附件：

- 有父消息时，上述字段必须全部有值。
- 父消息不存在时，记录日志并保留空值，不得伪造“未知发送人”。

本地文件上传：

- `sender_*`、`source_conversation_*`、`sent_at` 允许为空。
- `file_name`、`mime_type` 等文件元数据仍按现有逻辑处理。

## 5. Knowledge 改造

### 5.1 修改文件

`services/knowledge/internal/repository/postgres.go`

重点函数：

```go
TryMarkKnowledgeReady
```

### 5.2 查询策略

保留现有 `scanKnowledgeItem()` 状态检查逻辑，在同一个事务中额外查询元数据。

建议 SQL：

```sql
SELECT
    COALESCE(ki.source_message_id::text, a.message_id::text, ''),
    COALESCE(m.sender_identity_id::text, ''),
    COALESCE(NULLIF(m.sender_display_name, ''), NULLIF(ei.display_name, ''), ''),
    COALESCE(ci.platform, ''),
    m.sent_at,
    COALESCE(ci.name, ''),
    COALESCE(ci.platform, ''),
    COALESCE(ci.external_conversation_id, '')
FROM knowledge.knowledge_items ki
LEFT JOIN knowledge.attachments a
    ON a.id = ki.source_attachment_id
LEFT JOIN knowledge.messages m
    ON m.id = COALESCE(ki.source_message_id, a.message_id)
LEFT JOIN knowledge.external_identities ei
    ON ei.id = m.sender_identity_id
LEFT JOIN knowledge.conversation_ingestions ci
    ON ci.id = ki.conversation_ingestion_id
WHERE ki.id = $1
```

说明：

- 不使用不存在的 `knowledge.conversations`。
- 不读取不存在的 `attachments.sender_*`。
- `sender_platform` 和 `source_platform` 均取 `conversation_ingestions.platform`。

### 5.3 事件 payload

在现有 payload 中追加字段，不删除已有字段：

```go
payload, _ := json.Marshal(map[string]any{
    "resource_type": resourceType,
    "resource_id": resourceID,
    "knowledge_item_id": item.ID,
    "scope_type": scopeType,
    "scope_id": scopeID,
    "owner_user_id": nilString(item.OwnerUserID),
    "organization_id": nilString(item.OrganizationID),
    "knowledge_scope": item.KnowledgeScope,
    "source_conversation_id": nilString(item.ConversationID),
    "source_conversation_type": nilString(item.SourceConversationType),
    "source_audience_policy": item.SourceAudiencePolicy(),
    "content_version": item.ContentVersion,
    "acl_version": item.ACLVersion,
    "content_hash": item.ContentHash,
    "content_access_required": item.ContentAccessRequired,

    // 本次新增
    "source_message_id": nilString(sourceMessageID),
    "sender_identity_id": nilString(senderIdentityID),
    "sender_display_name": nilString(senderDisplayName),
    "sender_platform": nilString(sourcePlatform),
    "sent_at": sentAt,
    "source_conversation_name": nilString(conversationName),
    "source_platform": nilString(sourcePlatform),
    "external_conversation_id": nilString(externalConversationID),
})
```

保持 `schema_version=1`，这些字段是向后兼容的可选追加字段。

### 5.4 Knowledge 测试

增加或修改测试，覆盖：

1. 文本消息事件包含完整 sender 和 conversation 字段。
2. 聊天附件通过 `attachments.message_id` 取得发送人。

4. 附件没有父消息时不会 panic。

```python

    "title": title,
    "file_name": file_name,
    "heading_path": list(heading_path),
    "source_kind": context.resource_type,

    "sender_identity_id": context.sender_identity_id,
    "sender_display_name": context.sender_display_name,
    "sender_platform": context.sender_platform,

    "source_conversation_id": context.source_conversation_id,
    "source_conversation_name": context.source_conversation_name,
    "source_conversation_type": context.source_conversation_type,
    "source_platform": context.source_platform,
    "external_conversation_id": context.external_conversation_id,

    "source_message_id": context.source_message_id,
    "sent_at": context.sent_at,
}
```

同时扩展 `context_header` 的 strict 子字段：

```text
sender_identity_id
sender_display_name
sender_platform
source_conversation_id
source_conversation_name
source_conversation_type
source_platform
external_conversation_id
source_message_id
sent_at
```

如果只增加顶层字段而不同步增加 `context_header` 子字段，ES strict mapping 会拒绝新的 Chunk 文档。

保留 `Chunk` 现有独立字段：

- `source_conversation_id`
- `conversation_type`
- `message_id`
- `sent_at`

## 10. 回滚

Knowledge：

- 回滚代码后仍可处理旧格式事件。
- 已写入的新增字段不会影响旧消费者。

RAG：

- 回滚代码后新字段被忽略。
- ES mapping 新增字段可以保留，不影响旧查询。

本次不处理历史数据，因此没有历史回滚问题。

## 11. 风险

1. 附件没有父消息时无法取得 sender。
   - 处理：写日志并保留空值，不伪造数据。

2. 本地文件上传没有发送人。
   - 处理：明确为允许空值，不纳入覆盖率要求。

3. ES strict mapping 未先更新会导致 bulk 写入失败。
   - 处理：先更新 mapping，再部署 RAG 写入新字段。

4. 旧数据保持缺失。
   - 处理：本次明确不回填；需要时另开历史重建任务。
