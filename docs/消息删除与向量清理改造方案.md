# 消息删除与向量清理改造方案

- 文档状态：待审批
- 创建日期：2026-10-04
- 最近修订：2026-10-04
- 适用范围：Core、OpenFGA、Knowledge、RAG、Web、本机采集器
- 目标：为已采集消息提供权限清晰、可审计、可重试、向量可同步删除的删除链路。

## 1. 背景

当前系统已经具备消息采集、敏感分类、原文权限和设备绑定能力，但还没有消息删除能力。现有链路中只存在 RAG 问答会话删除，知识消息本身仍然只能新增和更新，不能安全退出查询、原文访问和向量检索。

消息删除不是单一的数据库删除操作。一条消息删除后可能影响：

- `knowledge.messages` 中的规范化消息。
- `knowledge.knowledge_items` 中的消息或附件知识项。
- `knowledge.attachments` 中的附件元数据和对象引用。
- `knowledge.message_private_content` 中的私人正文。
- 对象存储中的规范化正文、原文和附件对象。
- OpenFGA 中的查看、下载和临时授权关系。
- RAG PostgreSQL 中的 chunk、projection、branch 和派生候选数据。
- Elasticsearch display/protected 索引中的 chunk 和 embedding。
- 问答历史、引用、缓存和 Agent 记忆中的派生内容。
- 采集器重放时的唯一键冲突和内容复活风险。

因此，本方案采用“同步封禁访问、异步清理派生数据、延迟物理清除”的删除模型。

## 2. 目标与非目标

### 2.1 目标

1. 删除后立即阻止消息、原文、附件、搜索和问答访问。
2. 删除动作必须有明确的用户身份、组织范围和操作原因。
3. 向量删除必须覆盖 Elasticsearch 和 RAG PostgreSQL 派生数据。
4. 删除过程必须可审计、可重试、可追踪，并支持幂等调用。
5. 附件共享对象必须在确认没有有效引用后再物理删除。
6. 采集器重放不能使已删除消息重新变为可检索状态。
7. 私人内容与组织内容的删除权限必须分开。
8. 永久清理必须支持保留期、人工审计和后续合规扩展。

### 2.2 非目标

1. 删除系统内副本不等于删除微信、飞书等来源平台上的原始消息。
2. MVP 不提供普通成员直接删除任意组织群消息的能力。
3. MVP 不处理第三方 Embedding 服务已经接收过的文本副本。
4. MVP 不承诺在线删除完成后备份系统立即不存在历史副本。
5. MVP 不提供跨组织批量合规清除工作台，但数据模型应保留扩展空间。

## 3. 设计原则

### 3.1 删除不等于物理 `DELETE`

消息删除分为三个语义阶段：

- 可见性删除：业务接口、搜索、原文和附件立即不可访问。
- 派生数据删除：RAG 向量、chunk、授权关系和缓存被清理。
- 物理清除：达到保留期后删除正文和对象存储，只保留无正文审计墓碑。

接口返回成功时，至少要完成数据库事务内的可见性删除。向量和对象清理允许异步完成。

### 3.2 权限失败关闭

发生以下情况时，不得继续返回内容：

- 删除状态已经进入 `deleting`、`deleted` 或 `purged`。
- Core 授权服务不可用。
- Knowledge 无法确认 `lifecycle_status`。
- RAG 仍存在旧向量。
- 删除任务部分失败。

删除后即使向量尚未清完，Knowledge 和 RAG 的查询入口也必须拒绝该资源。

### 3.3 先撤销权限，再清理数据

FGA tuple 删除不是唯一安全边界。Knowledge 数据库中的生命周期状态、RAG 查询过滤和 OpenFGA 检查必须同时生效。

### 3.4 删除动作不等同于采集器授权

采集器或连接器负责提供消息，不代表采集者拥有组织知识删除权。组织知识删除权按组织角色判定。

### 3.5 保留删除墓碑

删除完成后保留资源 ID、操作者、时间、原因、内容版本和删除状态，不保留正文。墓碑用于：

- 阻止采集器重放后复活消息。
- 保证删除事件幂等。
- 支持审计和合规检查。
- 防止旧版本向量再次进入索引。

## 4. 当前能力与缺口

### 4.1 已有能力

- `knowledge.messages` 已存在 `lifecycle_status` 和 `vector_status` 字段。
- `knowledge.knowledge_items` 已存在 `lifecycle_status`、`acl_version` 和 `processing_status`。
- Knowledge 已存在 outbox，可发布 `knowledge.ready` 事件。
- RAG 已存在 `ProjectionStatus.DELETED` 状态。
- RAG chunk、snapshot 和 project 表已存在 `lifecycle_status`。
- Core 已支持资源关系同步和 OpenFGA tuple 删除。
- Core 已存在 Owner 和 Information Admin 角色。
- 附件对象存储已经支持删除接口。

### 4.2 当前缺口

1. `knowledge.messages.lifecycle_status` 当前只允许 `active`。
2. `knowledge.knowledge_items.lifecycle_status` 当前只允许 `active`。
3. 没有删除请求表和删除目标表。
4. 没有 `knowledge.deleted` 或 `knowledge.deletion.requested` outbox 事件。
5. RAG 没有按完整资源删除的全量向量能力，只有旧版本删除。
6. RAG 没有消费删除事件并更新 projection 状态的流程。
7. OpenFGA 模型没有 `delete` 或 `moderator` 关系。
8. 附件物理对象没有明确的删除引用计数流程。
9. 前端没有删除入口、权限状态和异步进度展示。
10. 采集器 upsert 尚未考虑已删除消息墓碑。

## 5. 删除对象与范围

### 5.1 单条消息

删除目标是消息及其全部有效附件。Knowledge 必须把消息展开成多个删除目标：

- 消息规范化内容。
- 消息 Knowledge Item。
- 消息附件元数据。
- 附件 Knowledge Item。
- 附件原始对象和解析文本对象。
- 关联授权和向量。

### 5.2 整个会话

按会话批量删除全部有效消息。该操作必须创建批次，而不是在一个 HTTP 请求中同步完成所有物理删除。

### 5.3 指定用户身份

按 `external_identities.mapped_user_id` 或身份映射批量删除某个用户产生的消息。该能力用于后续合规请求，不建议 MVP 首次开放。

### 5.4 只清理派生索引

用于修复错误的 RAG 索引，不改变 Knowledge 消息可见性。该能力仅对平台管理员或运维任务开放。

## 6. 权限模型

### 6.1 删除权限主体

| 主体 | 私人消息 | 组织群消息 | 附件 |
| --- | --- | --- | --- |
| 私人内容所有者 | 可直接删除 | 不适用 | 可直接删除 |
| 组织 Owner | 不适用 | 可直接删除 | 可直接删除 |
| 信息管理员 | 不适用 | 可直接删除 | 可直接删除 |
| 普通组织成员 | 不适用 | 只能发起删除申请 | 只能发起删除申请 |
| 本机采集者 | 不能删除组织消息 | 不能直接删除 | 不能直接删除 |
| 群聊创建者 | 不适用 | MVP 只能申请整会话删除 | 随消息处理 |
| 原始消息发送者 | 私人会话按所有者处理 | MVP 暂不开放自删 | 随消息处理 |

### 6.2 OpenFGA 建议

在现有模型基础上增加：

```text
type organization
  relations
    define member: [user]
    define information_admin: [user]

type knowledge_item
  relations
    define owner: [user]
    define organization: [organization]
    define conversation_group: [conversation_group]
    define moderator: information_admin from organization
    define delete: owner or moderator
```

角色授予和撤销时必须同步维护 `organization#information_admin` tuple。

### 6.3 权限判断顺序

1. 验证当前用户是否属于目标资源所属组织。
2. 检查当前用户是否具备 `delete` 权限。
3. 私人内容优先检查 `owner`。
4. 组织内容检查 `information_admin` 或 Owner。
5. 普通成员只允许创建删除申请，不允许直接调用执行删除接口。
6. 删除接口失败时不得退回“仅隐藏当前用户”的弱语义。

## 7. 删除状态机

建议使用以下状态：

```text
active
  -> deleting
  -> deleted
  -> purged

deleting
  -> delete_failed
  -> deleting
```

状态定义：

- `active`：正常可见。
- `deleting`：已隐藏，授权已撤销，后台清理进行中。
- `deleted`：在线数据不可访问，向量和派生索引已清理，等待物理清除。
- `purged`：正文和对象已物理清除，仅保留审计墓碑。
- `delete_failed`：隐藏仍然有效，但向量、授权或对象清理失败，后台继续重试。

`delete_failed` 不是恢复状态。用户不能通过该状态重新看见内容。

## 9. 接口设计

### 9.1 发起删除

```text
POST /api/knowledge/v1/deletion-requests
```

请求：

```json
{
  "scope_type": "message",
  "scope_id": "message-uuid",
  "reason": "用户申请删除",
  "idempotency_key": "client-generated-key"
}
```

权限规则：

- 直接执行删除权限：创建后立即进入 `approved/executing`。
- 普通成员：创建后进入 `pending`，等待信息管理员审批。

### 9.2 查询删除状态

```text
GET /api/knowledge/v1/deletion-requests/{request_id}
```

返回：

```json
{
  "status": "executing",
  "visibility": "hidden",
  "authorization": "revoked",
  "vector": "deleting",
  "object": "pending",
  "completed_targets": 2,
  "total_targets": 3
}
```

### 9.3 审批删除申请

```text
POST /api/knowledge/v1/deletion-requests/{request_id}/approve
POST /api/knowledge/v1/deletion-requests/{request_id}/reject
```

只有组织 Owner 和信息管理员可以审批。

## 10. 端到端删除流程

### 10.1 发起与权限检查

1. Web 调用 Knowledge 创建删除申请。
2. Knowledge 解析目标消息、附件和 Knowledge Item。
3. Knowledge 调用 Core 进行 `delete` 权限检查。
4. 普通成员创建 `pending` 申请，管理员直接进入执行。
5. 审批通过后，Coordinator 启动删除流程。

### 10.2 同步隐藏与撤销授权

同一数据库事务内必须完成：

1. 将消息和 Knowledge Item 标记为 `deleting`。
2. 增加 `content_version` 或 `acl_version`，使旧事件和旧缓存失效。
3. 写入删除墓碑。
4. 将删除目标写入 `deletion_targets`。
5. 写入权限撤销 outbox。
6. 写入 `knowledge.deletion.requested` outbox。
7. 提交事务。

通过 API 查询消息后，此时普通接口不再返回内容。

### 10.3 OpenFGA 与临时授权撤销

Core 收到权限撤销请求后：

1. 删除 `knowledge_item`、`knowledge_original`、`attachment_meta` 和 `attachment_content` 的旧关系。
2. 撤销 `viewer` 和 `downloader` 临时授权。
3. 取消未完成的原文和下载申请。
4. 标记已批准申请为 revoked。
5. 返回撤销结果。

Knowledge 只有在授权撤销成功后才把 `auth_state` 改成 `revoked`。

### 10.4 RAG 向量删除

Knowledge 发布：

```text
knowledge.deletion.requested
```

Payload 至少包含：

```json
{
  "deletion_request_id": "uuid",
  "deletion_target_id": "uuid",
  "knowledge_item_id": "uuid",
  "resource_type": "message",
  "resource_id": "uuid",
  "content_version": 3,
  "acl_version": 7,
  "scope_type": "organization",
  "scope_id": "uuid",
  "requested_by": "uuid",
  "reason": "用户申请删除",
  "purge_after": "2026-10-11T00:00:00Z"
}
```

RAG 必须执行：

1. 校验事件 schema 和资源身份。
2. 以 `deletion_target_id` 和 `knowledge_item_id` 做幂等控制。
3. 立即将 projection 标记为 `deleted` 或删除。
4. 删除 display 和 protected 两套 Elasticsearch 中的全部相关 chunk。
5. 删除或失效 PostgreSQL 中的 chunk、chunk_branches 和 projection。
6. 清理候选提及、快照派生引用和其他包含正文片段的派生记录。
7. 清理 embedding 缓存和搜索缓存。
8. 发布 `knowledge.rag.deleted` 回调。
9. 回调失败时保持任务可重试，不重新激活正文。

向量删除条件必须同时覆盖：

```text
resource_id
knowledge_item_id
全部 content_version
display/protected 两类索引
```

不能只删除当前版本，也不能只把文档标成 `inactive` 后继续保留正文和 embedding。

### 10.5 对象存储删除

消息规范化正文和附件对象按下述规则处理：

1. 先检查 `object_ref` 是否仍被其他有效附件或知识项引用。
2. 引用计数大于零时，仅解除当前逻辑引用。
3. 引用计数为零时，将 `object_state` 改为 `deleting`。
4. 删除成功后再改为 `deleted`。
5. 删除失败时记录错误并重试。

附件原对象、原始解析文本和 display 解析文本必须分别处理。

### 10.6 进入 deleted

当以下条件全部满足时，删除目标进入 `deleted`：

- 消息和 Knowledge Item 已隐藏。
- OpenFGA 和临时授权已撤销。
- RAG 向量和相关派生数据已删除。
- RAG 已返回成功回调。

此时用户仍然看不到内容，但物理对象可能因保留期尚未删除。

### 10.7 物理清除

达到 `purge_after` 后执行：

1. 再次检查是否存在 Legal Hold 或审计冻结。
2. 删除正文和对象存储。
3. 删除无审计价值的临时派生数据。
4. 保留消息 ID、删除请求、操作者、时间和原因。
5. 将消息和 Knowledge Item 改为 `purged`。

## 11. 采集器与重放处理

当前采集器可以重新上报相同 `external_message_id`。删除后必须增加以下规则：

1. 已删除消息仍保留唯一键和墓碑。
2. upsert 发现墓碑时，不得恢复正文和 lifecycle。
3. 新采集版本只能记录“尝试重放”审计，或进入隔离区等待人工处理。
4. 如果业务要求允许重新采集，必须由信息管理员明确发起“恢复采集”，不能隐式复活。
5. 删除事件中的 `content_version` 必须大于旧版本，防止旧 RAG 事件覆盖删除状态。

## 12. 一致性、幂等和失败处理

### 12.1 幂等

- 删除申请使用 `idempotency_key`。
- 删除目标使用唯一资源组合。
- RAG 使用 `deletion_target_id` 和 `knowledge_item_id` 去重。
- 重复事件不能重复删除或产生错误状态。

### 12.2 重试

- OpenFGA 撤销失败：指数退避重试。
- RAG 向量删除失败：保留 `delete_failed` 并重试。
- 对象存储删除失败：只重试对象阶段，不重新开放可见性。
- 回调失败：保持在线隐藏，不能回滚为 `active`。

### 12.3 死信和告警

建议增加指标：

```text
deletion_pending_total
deletion_failed_total
deletion_visibility_latency_seconds
deletion_vector_latency_seconds
deletion_object_latency_seconds
deletion_oldest_pending_seconds
```

超过阈值后告警平台管理员。

## 13. 查询和缓存失效

以下入口必须检查生命周期并拒绝删除内容：

- 会话详情消息列表。
- 知识库列表。
- 联系人和会话上下文。
- 原文查看接口。
- 附件预览和下载接口。
- RAG 搜索。
- RAG 问答。

以下缓存必须失效：

- 搜索 scope 缓存。
- 会话摘要缓存。
- Embedding 缓存。
- Agent 记忆候选。
- 问答引用和上下文摘要。

问答历史中的旧回答可以保留问题，但引用已删除消息时必须：

- 从回答展示中移除引用。
- 阻止再次打开原文。
- 后续重新问答时不再召回。
- 如回答正文包含敏感片段，应重新脱敏或标记不可用。

## 14. 前端交互

### 14.1 有删除权限

消息菜单显示“删除”。

确认框必须说明：

- 删除后立即从知识库、搜索和问答中移除。
- 原始平台消息不会被删除。
- 物理清理可能存在保留期。

### 14.2 普通成员

消息菜单显示“申请删除”。

提交后展示状态：

```text
待审批
审批通过，正在隐藏
权限已撤销
索引清理中
删除完成
后台重试中
```

### 14.3 管理员审批

审批页面展示：

- 申请人和组织。
- 消息发送人、时间和所属群。
- 脱敏文本摘要。
- 删除原因。
- 影响的消息和附件数量。
- 是否涉及共享私人内容。

## 15. 分阶段实施

### 阶段 1：数据模型和权限

- 扩展消息和 Knowledge Item 生命周期约束。
- 新增 deletion request、target 和 audit 表。
- 增加 OpenFGA `delete` 和 `information_admin` 关系。
- 增加 Core `delete` 权限检查。

### 阶段 2：Knowledge 删除编排

- 实现删除申请、审批、隐藏和授权撤销。
- 增加删除 outbox 事件。
- 处理采集器重放墓碑。
- 完成审计和状态查询。

### 阶段 3：RAG 向量删除

- 增加删除事件 schema 和消费者。

## 16. 验收标准

1. 私人所有者可以删除自己的私人消息。
2. 普通成员不能直接删除组织群消息。
3. 信息管理员和组织 Owner 可以删除组织群消息。
4. 删除提交成功后，所有在线接口立即看不到内容。
5. 删除后原文和附件下载返回拒绝。
6. OpenFGA 检查结果为拒绝，临时 viewer/downloader 授权被撤销。
7. display 和 protected Elasticsearch 中的相关向量均被删除。
8. RAG PostgreSQL 中不再存在有效 chunk 和 chunk branch。
9. 重复删除请求不会产生重复资源和错误状态。
10. 采集器重放相同消息不能恢复正文。
11. 附件对象仍被其他有效资源引用时不会被误删。
12. 删除失败时内容保持隐藏，后台可重试。
13. 审计日志能够还原申请人、审批人、执行人和删除阶段。
14. 物理清理完成后只保留资源 ID 和审计信息。

## 17. 回滚策略

1. 回滚时停止接受新删除请求。
2. 已进入 `deleting` 或 `deleted` 的资源继续清理，不回滚为 `active`。
3. 恢复旧的读取接口时必须保留生命周期过滤。
4. 恢复前验证 OpenFGA tuple 未残留。
5. 回滚不得重新发布已删除资源的 `knowledge.ready` 事件。

4. 永久物理清理是否需要双人审批。
5. 组织信息管理员删除操作是否需要通知消息发送者。
6. 共享私人内容被原所有者删除后，组织副本是否同步删除。
7. 问答历史中的引用是自动移除，还是保留“来源已删除”占位。
8. MVP 是否同时覆盖附件正文和对象存储物理删除。

## 19. 建议审批结论

建议 MVP 先采用以下口径：

- 私人所有者可直接删除私人内容。
- 组织 Owner 和信息管理员可直接删除组织消息。
- 普通成员只能申请删除。
- 删除立即隐藏并撤销授权。
- 向量和派生索引异步删除，但删除完成前也必须被查询链路过滤。
- 默认保留 7 天后物理清理。
- 原始平台消息不删除。
- 附件对象按引用计数清理。
- 永久清理和跨用户批量删除暂不开放给普通管理员。

### 20.3 后续阶段计划

#### 阶段 A：补删除审批与执行编排

目标：让普通成员的删除申请能够被审批，并在审批通过后进入真实删除流程。

实施内容：

1. 增加删除申请审批接口：
   - `POST /api/knowledge/v1/deletion-requests/{request_id}/approve`
   - `POST /api/knowledge/v1/deletion-requests/{request_id}/reject`
2. 审批权限限定为组织 Owner 和信息管理员。
3. 审批通过时写入 `reviewer_user_id`、`reviewed_at` 和审计日志。
4. 审批通过后把 `pending` 改为 `executing`。
5. 审批通过后执行同步隐藏：
   - 消息切换为 `deleting`
   - 知识项切换为 `deleting`
   - 写入删除墓碑
   - 发布 `knowledge.deletion.requested`
6. 审批拒绝只更新状态和审计，不修改内容可见性。
7. 重复审批必须幂等，不能重复隐藏或重复发布事件。
8. 前端增加“待我审批”和删除状态展示入口。

验收标准：

- 普通成员提交后内容仍可见，但申请进入待审批。
- 管理员审批通过后内容立即不可见。
- 重复审批不会产生重复删除目标或重复事件。
- 拒绝申请不会影响原内容。
- 审批操作可以在审计日志中还原申请人和审批人。

#### 阶段 B：补授权撤销与 RAG 回调

目标：让删除结果具备授权一致性和向量删除完成确认。

实施内容：

1. Knowledge 在删除执行阶段调用 Core 撤销资源关系：
   - `knowledge_item`
   - `knowledge_original`
   - `attachment_meta`
   - `attachment_content`
2. 撤销 `viewer` 和 `downloader` 临时授权。
3. 取消未完成的原文和下载申请。
4. 已批准申请标记为 revoked。
5. 成功后更新 `auth_state=revoked`。
6. RAG 删除完成后发布 `knowledge.rag.deleted`。
7. Knowledge 消费回调并更新 `vector_state=deleted`。
8. RAG 删除失败时更新 `vector_state=failed` 并记录错误。
9. 增加重试和死信处理，失败状态不能恢复内容可见性。
10. 只有隐藏、授权撤销和向量删除全部完成后，删除目标才进入 `deleted`。

验收标准：

- 删除后 OpenFGA 检查稳定返回拒绝。
- 原文和附件临时授权被撤销。
- RAG 删除完成能够回写 Knowledge 状态。
- RAG 删除失败时任务进入可重试状态。
- 删除过程中任何阶段失败，内容都保持不可见。

#### 阶段 C：补对象存储和保留期清理

目标：完成附件和正文对象的物理清除，并保留审计墓碑。

实施内容：

1. 实现附件对象引用计数。
2. 识别共享对象是否仍被其他有效附件或知识项引用。
3. 引用计数大于零时只解除当前逻辑引用。
4. 引用计数为零时推进 `object_state=deleting`。
5. 删除以下对象：
   - `attachments.object_ref`
   - `attachments.extracted_original_ref`
   - `attachments.extracted_display_ref`
6. 删除成功后推进 `object_state=deleted`。
7. 删除失败时记录 `object_state=failed` 和错误信息。
8. 增加后台 `PurgeDeletionRequests` 任务。
9. 扫描达到 `purge_after` 的删除目标。
10. 检查 Legal Hold 或审计冻结。
11. 物理清除正文和对象。
12. 将消息和知识项推进为 `purged`。
13. 只保留消息 ID、删除请求、操作者、原因和时间等审计信息。

验收标准：

- 附件对象仍被其他有效资源引用时不会被误删。
- 无引用对象能够被物理删除。
- 对象删除失败不会重新开放内容。
- 达到保留期后可以进入 `purged`。
- 物理清除完成后不再保留正文。

#### 阶段 D：补查询兜底与引用读时校验

目标：保证删除后的资源无法被任何在线入口再次读取，同时不回溯改写问答历史。旧回答和旧引用保留原样，只有在用户再次点击来源时才重新校验资源状态。

设计口径：

- 问答历史视为不可变记录，不重写历史回答，不批量修改旧引用。
- 引用记录只保存资源类型和资源 ID，不保存正文、对象地址、预签名 URL 或可直接访问的缓存地址。
- 点击“预览来源”或“跳转原文”时，必须重新向 Knowledge 解析资源。
- 资源已删除时，后端返回明确的删除状态，前端统一提示“该资源已被删除”或“该资源不可用或已被删除”。
- 删除后的资源不能仅靠前端提示拦截，后端必须拒绝返回正文、附件内容和下载地址。
- 已删除、无权限、暂不可用必须区分处理，不能把无权限误报成已删除。

实施内容：

1. 附件预览和下载增加生命周期检查。
2. 联系人上下文和联系人画像增加删除过滤。
3. RAG 新搜索和新问答在召回阶段过滤删除目标。
4. 旧问答的历史回答和引用列表保持不变。
5. 旧引用点击时重新解析来源资源，不直接使用历史快照打开预览。
6. 资源已删除时统一返回 `resource_deleted`。
7. 资源无权限时继续走现有权限申请流程。
8. 资源暂时不可用时返回可重试状态，不暴露删除状态。
9. Agent 记忆和摘要如果作为新回答的召回来源，读取时过滤删除资源；不回溯清洗历史记忆。
10. 搜索 scope 和 Embedding 缓存执行读时校验；历史缓存不得覆盖删除状态。
11. 增加统一 fail-closed 和引用跳转测试。

建议返回契约：

```json
{
  "code": "resource_deleted",
  "message": "resource has been deleted",
  "details": {
    "resource_type": "message",
    "resource_id": "..."
  }
}
```

HTTP 状态建议使用 `410 Gone`。响应不得包含被删除资源的正文、脱敏正文、标题、附件名、下载地址或对象引用。

前端行为：

- 来源正常：按现有逻辑打开预览或跳转原文。
- 来源已删除：不打开预览、不下载、不跳转，直接提示“该资源已被删除”。
- 来源无权限：继续显示申请查看原文或申请下载。
- 来源暂不可用：提示“资源暂不可用，请稍后重试”，不显示删除状态。

明确不做：

- 不重写问答历史。
- 不批量修改历史引用。
- 不重写 AI 回答正文。
- 不删除历史问答消息。
- 不要求清理所有历史缓存副本。
- 不在本阶段处理合规级的历史回答回填。

验收标准：

- 删除资源后，旧回答和旧引用仍保持原样。
- 点击旧引用会重新校验来源，不会直接命中历史快照。
- 已删除来源稳定返回 `resource_deleted`。
- 前端能区分“已删除”“无权限”“暂不可用”三种情况。
- 已删除来源不会打开预览、不会下载附件、不会跳转原文。
- 删除后的资源不会出现在新的搜索和问答结果中。
- 删除回调尚未完成时，新的搜索和问答也不会返回该资源。
#### 阶段 E：单条删除治理与运维

2. 支持按用户身份批量删除。
3. 支持批量审批。
4. 增加批次、分页、断点续跑和失败隔离。
5. 增加跨会话批量审计汇总。
6. 增加大批量删除的执行协调、限流和回滚策略。

验收标准：

- 整会话删除可分批执行，不会阻塞单个 HTTP 请求。
- 批量删除有进度、失败重试和审计记录。
- 大批量删除不会影响单条删除链路和其他在线查询。

### 20.4 推荐实施顺序

1. 先完成阶段 A：审批和执行编排。
2. 再完成阶段 B：授权撤销、RAG 回调和状态回写。
3. 然后完成阶段 C：对象存储和保留期物理清除。
4. 阶段 D：查询兜底和缓存失效可以穿插在 B/C 之间。
5. 阶段 E：单条删除治理与运维。
6. 阶段 F：批量与合规删除最后实施。

原因：

- 没有审批，普通成员申请不会真正执行。
- 没有授权撤销，删除后可能残留可访问关系。
- 没有 RAG 回调，Knowledge 无法确认向量是否清完。
- 没有对象存储删除，删除只完成在线隐藏和索引清理。
- 没有查询兜底，派生页面仍可能绕过删除状态。

### 20.5 删除审批与治理页面放置

- 补充日期：2026-10-05
- 目的：明确删除申请、审批操作和管理审计分别放在哪个页面，避免普通成员看到不属于自己的治理入口。

删除能力不应集中在一个“大而全”的删除页面，而应按照使用者角色拆成三个入口。

#### 消息详情页：发起与状态查看

面向普通成员和内容所有者，只显示当前消息的删除动作和申请状态。

页面行为：

- 有直接删除权限时显示“删除”。
- 没有直接删除权限时显示“申请删除”。
- 提交后显示“待审批”“已通过”“已拒绝”或执行失败原因。
- 不展示其他申请人的删除申请。
- 不提供审批操作。

该入口负责回答“我能不能删这条消息，以及我的申请现在是什么状态”。

#### 个人主页：待我审批

面向组织 Owner 和信息管理员，作为日常审批入口。

建议复用个人主页已有的权限申请区域：

```text
我发起的 / 待我审批
```

删除申请应与原文查看、附件下载等权限申请统一进入“待我审批”列表，因为在管理员视角它们都属于需要处理的申请。

待审批列表至少展示：

- 申请人。
- 消息发送人和所属群。
- 脱敏后的消息摘要。
- 删除原因。
- 影响的消息和附件数量。
- 是否涉及共享私人内容。
- 通过和拒绝操作。

删除审批完成后，申请进入执行状态，后续进度可以在同一列表或组织治理页面查看。

#### 组织页：内容治理

面向组织 Owner 和信息管理员，用于历史记录、执行状态和审计查询，不适合放在“我的组织”页的成员管理区域中。

建议在组织页增加独立标签，例如：

```text
内容治理
```

该标签下提供：

- 删除申请历史：
  - 待审批
  - 已通过
  - 已拒绝
  - 执行中
  - 已完成
  - 失败
- 删除执行进度：
  - 可见性状态
  - 授权撤销状态
  - 向量删除状态
  - 对象存储清理状态
- 删除审计日志：
  - 申请人
  - 审批人
  - 审批时间
  - 执行时间
  - 失败原因
- 指标和告警入口：
  - 删除积压
  - 删除失败数
  - 最老待处理任务时长

该页面只对组织 Owner 和信息管理员可见。普通成员不得看到入口，避免出现“页面可进入但接口返回 403”的体验问题。

#### 私人消息与组织消息的区别

- 私人消息由所有者直接删除，不进入组织审批队列。
- 组织群聊消息才进入组织删除审批。
- 共享私聊内容转入组织后，按组织知识处理，需要组织审批。
- 前端必须明确区分“直接删除”和“申请删除”，避免管理员误以为私人删除也需要审批。

#### 最终页面职责

```text
消息详情页    -> 发起删除 / 查看本人申请状态
个人主页      -> 待我审批（与原文和下载权限申请合并）
组织页        -> 内容治理（历史、执行进度、审计、指标告警）
```

阶段 A 已覆盖消息详情页和个人主页的基础入口。阶段 E 需要补齐组织页的内容治理入口、审计查询和指标告警展示。
