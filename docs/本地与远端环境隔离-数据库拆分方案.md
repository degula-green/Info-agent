# 本地与远端环境隔离：数据库、Redis 与对象存储拆分方案

## 1. 背景

当前本地开发环境和远端服务器可能共用同一套中间件：

- PostgreSQL：`123.57.175.182:5432/info-agent`
- Redis：`123.57.175.182:6379/1`
- MinIO：`123.57.175.182:9000`

由于 Agent Task、桌面设备、Knowledge 数据、RAG 数据和 Worker Stream 都在这些共享资源中，本地和远端虽然服务地址不同，实际上属于同一套任务和数据空间。

已经观察到的影响：

- 本地旧 Worker 与远端 Worker 竞争消费 `agent:tasks:local`
- 本地进程使用旧代码处理远端任务
- 桌面设备记录在远端 PostgreSQL 中长期保持 `active`
- 本地和远端看到同一批 Agent Task、设备和桌面任务
- 停止本地进程不会自动撤销或下线设备记录
- 旧设备可能被远端选中，导致表单任务超时

因此，只拆 Redis DB 不足以完成环境隔离。至少需要同时拆 PostgreSQL 数据空间、Redis DB 和 MinIO bucket。

## 2. 目标

1. 本地测试环境和远端运行环境互不消费任务。
2. 本地和远端拥有独立的 Agent Task、设备和桌面任务记录。
3. 本地和远端拥有独立的 Redis Stream、消费者组和待处理事件。
4. 本地和远端拥有独立的文件 bucket，避免对象互相覆盖。
5. 远端现有数据不需要迁移，降低实施风险。
6. 为后续设备在线状态和任务归属治理提供清晰边界。

## 3. 非目标

- 本方案不修改表单浏览器和桌面设备的业务逻辑。
- 本方案不决定桌面设备在线 TTL 的最终参数。
- 本方案不迁移生产用户、消息和权限数据到本地。
- 本方案不把 Redis 逻辑 DB 当作完整资源隔离。

Redis 逻辑 DB 只能隔离 key namespace，不能隔离 CPU、内存、持久化和实例故障。

## 4. 推荐方案

### 4.1 总体原则

保持远端现状不变，新建一套干净的本地开发数据空间：

```text
远端环境：
  PostgreSQL database: info-agent
  Redis logical DB:    1
  MinIO buckets:       info-agent / agent-temp

本地开发环境：
  PostgreSQL database: info-agent-dev
  Redis logical DB:    2
  MinIO buckets:       info-agent-dev / agent-temp-dev
```

该方案优先保护远端现有数据，不需要迁移远端数据库，只需要创建新本地资源并修改本地环境变量。

### 4.2 为什么不先迁远端

不建议先把远端切到新的空 Redis DB 或新 PostgreSQL database，原因如下：

- 远端可能仍有 pending Outbox、待消费 Stream 和未完成 Task。
- 切换后 old Redis DB 中的事件不会自动进入新 DB。
- PostgreSQL 数据迁移会产生停机窗口和回滚复杂度。
- 桌面设备密钥、加密数据和文件 bucket 需要保持一致。
- 当前更迫切的问题是把本地测试从远端数据空间中剥离。

如果必须迁移远端，应单独制定生产迁移方案，不能与本地隔离方案混在一起。

## 5. 目标拓扑

```text
                    PostgreSQL                 Redis                 MinIO
远端控制面  ->  info-agent DB             ->  DB 1               ->  info-agent
                                                                    agent-temp

本地控制面  ->  info-agent-dev DB         ->  DB 2               ->  info-agent-dev
                                                                    agent-temp-dev
```

两套控制面各自包含：

```text
Core
Knowledge
RAG Service / Worker
Agent Service / Workers
Nginx / Web
```

桌面端必须只轮询其中一个控制面。不能让同一个桌面进程根据环境自动切换远端和本地 API。

## 6. 环境变量矩阵

以下是逻辑变量名，具体值使用各自环境文件维护，不写入仓库。

### 6.1 远端环境

远端继续使用现有值：

```text
CORE_DATABASE_URL=.../info-agent
CORE_REDIS_URL=.../1
CORE_REDIS_DATABASE=1

KNOWLEDGE_DATABASE_URL=.../info-agent
KNOWLEDGE_DATABASE_SCHEMA=knowledge
KNOWLEDGE_REDIS_URL=.../1

RAG_DATABASE_URL=.../info-agent
RAG_DATABASE_SCHEMA=rag_mvp
RAG_REDIS_URL=.../1
RAG_REDIS_DATABASE=1

AGENT_DATABASE_URL=.../info-agent
AGENT_DATABASE_SCHEMA=agent
AGENT_REDIS_URL=.../1
AGENT_REDIS_INBOUND_STREAM=agent:tasks:local

CORE_MINIO_BUCKET=info-agent
KNOWLEDGE_MINIO_BUCKET=info-agent
RAG_MINIO_SOURCE_BUCKET=info-agent
AGENT_ATTACHMENT_MINIO_BUCKET=agent-temp
```

### 6.2 本地开发环境

本地改为新的数据空间：

```text
CORE_DATABASE_URL=.../info-agent-dev
CORE_REDIS_URL=.../2
CORE_REDIS_DATABASE=2

KNOWLEDGE_DATABASE_URL=.../info-agent-dev
KNOWLEDGE_DATABASE_SCHEMA=knowledge
KNOWLEDGE_REDIS_URL=.../2

RAG_DATABASE_URL=.../info-agent-dev
RAG_DATABASE_SCHEMA=rag_mvp
RAG_REDIS_URL=.../2
RAG_REDIS_DATABASE=2

AGENT_DATABASE_URL=.../info-agent-dev
AGENT_DATABASE_SCHEMA=agent
AGENT_REDIS_URL=.../2
AGENT_REDIS_INBOUND_STREAM=agent:tasks:local

CORE_MINIO_BUCKET=info-agent-dev
KNOWLEDGE_MINIO_BUCKET=info-agent-dev
RAG_MINIO_SOURCE_BUCKET=info-agent-dev
AGENT_ATTACHMENT_MINIO_BUCKET=agent-temp-dev
```

注意：部分服务同时支持 URL 中的 DB index 和独立 `*_REDIS_DATABASE` 环境变量。两者必须一致，例如：

```text
AGENT_REDIS_URL=redis://host:6379/2
AGENT_REDIS_DATABASE=2
```

不能只改 URL，导致代码中的显式 DB index 覆盖 URL。

## 7. 实施步骤

### 第一步：清点和备份

1. 记录远端 PostgreSQL 当前 database、schema、大小和连接数。
2. 备份远端环境文件。
3. 记录远端 Redis DB 1 的 Stream、Consumer Group 和 pending 数量。
4. 记录远端 MinIO bucket 和对象数量。
5. 备份本地当前环境文件。
6. 确认本地环境没有尚未导出的测试数据。

建议保存但不提交：

```text
pg_dump -Fc info-agent > info-agent-before-split.dump
cp docker/.env.server docker/.env.server.before-split
cp services/agent/.env services/agent/.env.before-split
cp services/rag/.env services/rag/.env.before-split
cp services/knowledge/.env services/knowledge/.env.before-split
cp services/core/.env services/core/.env.before-split
```

备份文件可能包含凭据和业务数据，不应提交到 Git。

### 第二步：创建本地 PostgreSQL database

在 PostgreSQL 中创建：

```sql
CREATE DATABASE "info-agent-dev";
```

不要通过 `CREATE SCHEMA` 只拆 schema，原因：

- Agent、Knowledge、RAG、Core 都使用固定 schema 名称。
- 多套 service 同时配置不同 schema 容易遗漏。
- 设备、任务和消息之间存在跨服务关系。
- 独立 database 更容易备份、恢复和清理。

创建完成后，使用项目已有迁移流程初始化：

1. Core 使用其启动迁移流程。
2. Knowledge 使用 `knowledge-migrate` 或对应 Go migration。
3. RAG 执行其 schema migration。
4. Agent 执行：

```text
python -m app.infrastructure.postgres.migrate
```

不要手工只创建部分表。

### 第三步：创建 Redis 逻辑 DB

选择 DB 2：

```text
Redis DB 1 = 远端
Redis DB 2 = 本地
```

验证 Redis 是否允许 `SELECT 2`。如果使用 Redis Cluster 或代理，逻辑 DB 可能不可用，此时应改用独立 Redis 实例或 key prefix。

初始化后检查：

```text
INFO keyspace
XLEN knowledge:ready
XLEN agent:tasks:local
XINFO GROUPS knowledge:ready
XINFO GROUPS agent:tasks:local
```

DB 2 初始应为空。不要复制远端 Stream pending entries。

### 第四步：创建本地 MinIO bucket

创建：

```text
info-agent-dev
agent-temp-dev
```

本地服务只写这些 bucket。不要复用远端的：

```text
info-agent
agent-temp
```

如果后续需要导入部分测试附件，应在导入前确认：

- 加密密钥可用。
- 文件元数据与数据库记录一致。
- 对象 key 不会覆盖远端对象。

### 第五步：修改本地环境文件

修改以下本地文件：

```text
services/core/.env
services/knowledge/.env
services/rag/.env
services/agent/.env
```

只改本地文件，远端 `docker/.env.server` 保持不动。

本地修改完成后，先不要启动 Worker，只启动 Core、Knowledge、RAG 和 Agent API，检查健康状态和数据库连接。

### 第六步：初始化本地数据

本地是干净 database，不包含远端用户、组织、设备和权限数据。需要创建本地测试数据：

1. 注册本地测试用户。
2. 创建本地测试组织。
3. 初始化本地 OpenFGA 关系。
4. 为本地桌面端重新配对设备。
5. 创建本地测试知识库和会话。

不要直接复制远端设备 private key。每个环境应有自己的设备身份和密钥。

### 第七步：启动本地 Worker

数据库和 API 验证通过后，才启动：

```text
RAG Worker
Agent Knowledge Worker
Agent Task Worker
```

本地 Worker 必须连接到：

```text
PostgreSQL: info-agent-dev
Redis:       DB 2
```

### 第八步：验证环境不再串任务

创建本地任务，确认：

- 只出现在 `info-agent-dev`
- 只写入 Redis DB 2
- 只由本地 Worker 处理
- 不会出现在远端任务列表

创建远端任务，确认：

- 只出现在远端 `info-agent`
- 只写入 Redis DB 1
- 只由远端 Worker 处理
- 不会出现在本地任务列表

## 8. 桌面设备处理

桌面设备绑定在 PostgreSQL 中，因此数据库拆分后，本地和远端设备完全独立。

正确关系：

```text
远端桌面设备
  -> 轮询 https://39.97.235.59
  -> 绑定远端数据库

本地桌面设备
  -> 轮询 http://localhost:<agent-port>
  -> 绑定本地 info-agent-dev
```

同一个物理电脑可以同时安装两套客户端或使用两个 userData 目录，但必须：

- 使用不同 device_id
- 连接不同 Agent API
- 不把本地设备记录导入远端
- 不把远端设备记录导入本地

停止某个环境的服务不会自动撤销该环境的设备记录。设备在线状态治理是后续独立事项。

## 9. 推荐运行模式

### 9.1 只测试远端

```text
远端：
  Core / Knowledge / RAG / Agent / Worker 开启

本地：
  只运行 Web 或桌面客户端
  不运行本地 Agent Worker
  客户端指向远端
```

这是当前最安全、最快的测试方式。

### 9.2 测试完整本地栈

```text
远端：
  按需保留，但本地客户端不连接远端

本地：
  Core / Knowledge / RAG / Agent / Worker 全部使用 info-agent-dev + Redis DB 2
  桌面端单独配对本地设备
```

### 9.3 禁止的模式

```text
本地和远端共用 PostgreSQL
本地和远端共用 Redis DB
本地和远端同时消费相同 stream
本地和远端设备记录混用
```

## 10. 验收清单

### PostgreSQL

```sql
SELECT current_database();
SELECT current_schema();
```

确认：

- 本地服务全部返回 `info-agent-dev`
- 远端服务全部返回 `info-agent`
- 两边设备、任务、会话数量独立变化

### Redis

分别检查 DB 1 和 DB 2：

```text
INFO keyspace
XLEN knowledge:ready
XLEN agent:tasks:local
XINFO GROUPS knowledge:ready
XINFO GROUPS agent:tasks:local
```

确认：

- 远端 pending 不进入本地
- 本地 pending 不进入远端
- Consumer Group 独立
- Worker 不再互相抢任务

### MinIO

确认：

- 本地对象只写 `info-agent-dev` 和 `agent-temp-dev`
- 远端对象仍写 `info-agent` 和 `agent-temp`
- 本地清理 bucket 不影响远端

### Agent Task

1. 创建本地任务。
2. 轮询本地任务 API。
3. 轮询远端任务 API。
4. 确认任务不会跨环境出现。
5. 停止本地 Worker，确认远端任务仍可执行。
6. 停止远端 Worker，确认本地任务仍可执行。

## 11. 回滚方案

回滚只在本地环境执行，不影响远端：

1. 停止本地 Core、Knowledge、RAG、Agent 和 Worker。
2. 恢复本地环境文件备份。
3. 切回原 database、Redis DB 和 MinIO bucket。
4. 重新启动本地服务。
5. 验证远端服务和任务流未被修改。

如果在本地新环境中创建了需要保留的数据，回滚前必须单独导出，不能直接覆盖数据库。

## 12. 风险与限制

1. Redis DB 2 与 DB 1 仍在同一实例上，不是物理资源隔离。
2. PostgreSQL 新 database 可能仍在同一实例上，开发误操作不会影响远端 data namespace，但实例故障会影响两边。
3. 加密密钥与历史密文必须成对迁移，不能只迁其中一部分。
4. 桌面设备需要重新配对。
5. 本地 OpenFGA、JWT、refresh token 和 service token 需要自洽配置。
6. 本地和远端如果继续共享 MinIO 凭据，bucket 必须严格区分。
7. Redis Stream 名称可以相同，因为 DB 已隔离；如果后续改为独立 Redis 实例，也可以继续沿用相同名称。

## 13. 推荐实施顺序

```text
1. 备份远端和本地环境文件
2. 创建 info-agent-dev database
3. 创建 Redis DB 2
4. 创建 info-agent-dev / agent-temp-dev buckets
5. 执行本地数据库迁移
6. 修改本地服务环境文件
7. 启动本地基础服务
8. 初始化本地用户、组织、权限和设备
9. 启动本地 Worker
10. 验证本地和远端数据和任务完全隔离
11. 记录新的环境启动和排障手册
```

## 14. 结论

只修改远端 Redis DB 不能彻底解决环境混用问题，因为设备和任务的核心状态在 PostgreSQL。

推荐的最小完整方案是：

```text
远端保持现有 database、Redis DB 和 bucket 不变
本地新建 info-agent-dev、Redis DB 2 和 dev bucket
桌面设备按环境分别配对
本地与远端只共享物理中间件，不共享数据 namespace
```

完成该拆分后，本地 Worker、远端 Worker、设备记录和表单任务才会真正互不干扰。
