# 权限申请展示与历史脏数据治理方案

- 文档状态：已批准，实施完成
- 编写日期：2026-10-06
- 适用模块：Web 个人主页、Knowledge 删除申请、Core 原文访问申请
- 当前要求：按本方案实施，保留历史审计，不物理删除申请数据

## 0. 实施记录

- 已将个人主页权限申请拆分为“我发起的 / 待我审批 / 历史记录”三个视图。
- 删除申请接口已支持 `view=active|history|all`。
- 删除申请已补充申请人昵称、邮箱、目标摘要、阶段摘要、状态中文和审批能力字段。
- 前端默认隐藏终态历史记录，历史记录单独展示。
- 已新增隐藏但 pending 的删除申请自动修复任务。
- 保留 `cancelled`、`completed`、`failed`、`rejected`、`superseded` 审计记录，不执行物理删除。

## 1. 当前问题

个人主页的“权限申请”把不同类型、不同生命周期、不同责任人的申请混在同一个列表中，用户无法快速判断：

1. 哪些申请需要审批。
2. 哪些申请正在执行。
3. 哪些申请已经结束，只用于历史追溯。
4. 哪些申请是历史重复数据。

当前界面还存在以下具体问题：

- 删除申请标题直接显示 `requester_user_id`，例如 `7d0779ab-9ea4-409e-a51c-842b5b9fb875`。
- `cancelled`、`executing`、`superseded` 等状态没有完全中文化。
- “我发起的”默认展示全部历史记录，terminated 记录与进行中记录混排。
- 删除申请只显示顶层 `executing`，没有展示隐藏、向量、对象、权限四个子阶段。
- “待我审批”为空时没有解释为什么为空。

## 2. 当前数据事实

截至 2026-10-06 的只读核对结果：

```text
pending access requests       = 0
pending deletion requests     = 0
executing deletion requests   = 6
superseded deletion requests  = 5
```

因此当前“不能审批”不是按钮故障，而是当前没有 `pending` 状态的待审批申请。

现有数据可以分为四类：

| 类型 | 状态 | 是否属于脏数据 | 推荐展示 |
| --- | --- | --- | --- |
| 历史原文授权申请 | `cancelled` | 否 | 默认进入历史，不再参与审批 |
| 有效删除流程 | `executing` | 否 | 在“处理中”展示，并显示阶段 |
| 历史重复删除申请 | `superseded` | 是，但已治理 | 默认隐藏，可在历史/审计中查看 |
| 被旧流程修复的申请 | `executing` | 已修复 | 正常展示为处理中 |

当前 6 条 `executing` 申请不是重复申请，而是每个消息保留一条规范流程。其对象阶段在保留期结束后完成，不应显示为“待处理”或“脏数据”。

## 3. 总体设计原则

### 3.1 审批与历史分离

- “待我审批”只展示当前用户有权限处理、且状态为 `pending` 的申请。
- “我发起的”只展示当前用户可见的进行中申请。
- “历史记录”单独展示 `cancelled`、`completed`、`failed`、`rejected`、`superseded` 等终态记录。

### 3.2 不物理删除审计数据

- 历史申请继续保留在 `iam.access_requests` 和 `knowledge.deletion_requests`。
- 重复删除申请继续保留，状态统一为 `superseded`。
- 自动关闭的原文申请继续保留，状态统一为 `cancelled`。
- UI 通过过滤和聚合隐藏历史记录，不能通过数据库 `DELETE` 清理。

### 3.3 审批动作与执行状态分离

- 只有 `pending` 状态显示“通过/拒绝”按钮。
- `executing` 状态不显示审批按钮，只显示阶段进度。
- 管理员直接删除不产生 pending 申请，只产生执行记录。

### 3.4 不把 UUID 当标题

- 主标题展示用户可读名称和动作。
- 资源 UUID 只放在详情、复制字段或技术信息区域。
- 消息摘要、会话名称、平台、发送人优先展示。

## 4. 前端信息架构

权限申请面板调整为三个视图：

### 4.1 待我审批

用途：处理当前用户可审批的申请。

展示范围：

- Core 原文/附件访问：`status=pending`。
- Knowledge 删除申请：`status=pending`，且当前用户具备审批资格。
- 私聊共享访问申请：`status=pending`。

列表项：

- 标题：`张三 申请查看消息原文` / `李四 申请删除消息`。
- 副标题：平台、会话、发送人、消息摘要或文件名。
- 申请理由。
- 申请时间。
- 操作：`查看上下文`、`通过`、`拒绝`。

空状态：

```text
当前没有需要你审批的申请
```

当 `pending=0` 时，明确说明这是正常空状态，不是加载失败。

### 4.2 我发起的

用途：查看自己提交的进行中申请。

默认展示：

- `pending`
- `approved`，如果当前流程仍需要等待
- `executing`

不默认展示：

- `cancelled`
- `completed`
- `rejected`
- `failed`
- `superseded`

删除申请列表项建议展示：

```text
我 申请删除消息
飞书 · aims · 消息 012d… · 2026/10/5 21:39
原因：历史删除消息
状态：处理中
阶段：已隐藏 · 向量已清理 · 权限已撤销 · 对象保留中
```

### 4.3 历史记录

用途：审计和追溯，不作为默认审批入口。

展示范围：

- `cancelled`
- `completed`
- `failed`
- `rejected`
- `expired`
- `revoked`
- `superseded`

建议增加筛选项：

- 全部历史
- 已取消
- 已完成
- 已合并
- 已拒绝
- 执行失败

历史记录默认按时间倒序，最多展示最近 50 条，支持分页或“加载更多”。

## 5. 状态与文案映射

前端统一使用以下状态映射：

| 后端状态 | 中文文案 | 主题 | 是否可审批 |
| --- | --- | --- | --- |
| `pending` | 待审批 | 警告色 | 是 |
| `approved` | 已通过 | 成功色 | 否 |
| `executing` | 处理中 | 进行中 | 否 |
| `completed` | 已完成 | 成功色 | 否 |
| `rejected` | 已拒绝 | 中性/危险 | 否 |
| `failed` | 执行失败 | 危险色 | 否 |
| `cancelled` | 已关闭 | 中性 | 否 |
| `superseded` | 已合并 | 中性 | 否 |
| `expired` | 已过期 | 中性 | 否 |
| `revoked` | 已撤销 | 中性 | 否 |

删除申请额外展示阶段状态：

| 阶段 | 后端字段 | 中文文案 |
| --- | --- | --- |
| 可见性 | `visibility_state=hidden` | 已隐藏 |
| 向量 | `vector_state=deleted` | 向量已清理 |
| 权限 | `auth_state=revoked` | 权限已撤销 |
| 对象 | `object_state=pending` | 对象保留中 |
| 对象 | `object_state=deleted` | 对象已清理 |

对象阶段处于保留期时，应显示“对象保留中”及预计清理时间，不能只显示“执行中”。

## 6. 用户与资源展示规则

### 6.1 申请人展示

优先展示顺序：

1. `requester_nickname`
2. `requester_email`
3. `requester_user_id`

删除申请 DTO 应增加用户可读字段，例如：

```json
{
  "requester_display_name": "张三",
  "requester_user_id": "7d0779ab-...",
  "target_summary": "飞书 · aims · 消息 012d…",
  "status_label": "处理中"
}
```

前端只在兜底情况下展示完整 UUID；详情中允许展示，但不能作为主标题。

### 6.2 删除目标展示

删除申请优先展示：

1. 会话名称。
2. 平台。
3. 消息摘要。
4. 发送人。
5. 消息 ID 截断展示。

资源 ID 只在无摘要时展示，例如：

```text
消息 012d9261…
```

## 7. 后端接口调整建议

### 7.1 查询语义

当前接口：

```text
GET /deletion-requests?scope=mine|inbox&status=
```

建议增加视图维度：

```text
GET /deletion-requests?scope=mine|inbox&view=active|history|all&status=
```

规则：

- `scope=inbox`：只返回当前用户有权审批的 `pending` 申请。
- `scope=mine&view=active`：返回自己的 `pending/approved/executing`。
- `scope=mine&view=history`：返回自己的终态记录。
- `view=all`：仅审计页面使用。

### 7.2 返回字段

建议删除申请 DTO 增加：

```text
requester_display_name
requester_email
target_summary
status_label
stage_summary
stage_updated_at
can_review
can_cancel
```

其中：

- `can_review` 由后端按权限计算，前端不自行猜测。
- `stage_summary` 用于“我发起的”展示。
- `status_label` 用于统一文案。

### 7.3 列表聚合

继续保留消息级去重：

- 同一消息只返回一条有效申请。
- `superseded` 记录只出现在历史或审计视图。
- 同一资源的 `pending` 申请不能重复返回。

## 8. 脏数据处理方案

### 8.1 原则

不直接删除任何申请、目标和审计日志。脏数据通过状态修复、去重和展示隔离处理。

### 8.2 已识别类型

#### 类型 A：pending，但消息已隐藏

特征：

- request.status = `pending`
- message.lifecycle_status = `deleting`
- message.delete_request_id = request.id
- target.visibility_state = `hidden`

处理：

- 这是“规范申请但流程中断”，不是垃圾数据。
- 状态修复为 `executing`。
- 撤销授权，写 `auth_state=revoked`。
- 重置 `knowledge.deletion.requested` outbox 事件，重新交给 RAG。
- 写 `deletion.state_repaired` 审计。

#### 类型 B：同一消息多条有效删除申请

处理：

- 选择规范申请。
- 其他记录标记为 `superseded`。
- 增加消息级有效申请唯一索引。
- 保留原申请和目标记录，不物理删除。

#### 类型 C：已具备原文权限但仍 pending 的访问申请

处理：

- 查询当前 OpenFGA 权限。
- 当前已具备权限时标记为 `cancelled`。
- 记录 `review_note=current_permission_granted`。
- 默认从“待我审批”中移除，只在历史中查看。

#### 类型 D：长时间停留在 executing 的删除申请

处理：

- 检查四个阶段：
  - visibility
  - vector
  - auth
  - object
- 如果对象保留期未到，显示“对象保留中”。
- 如果所有阶段已完成但 request 未 completed，执行状态聚合修复。
- 如果阶段失败，显示失败阶段和错误原因。

### 8.3 历史数据展示隔离

| 数据状态 | 默认列表 | 历史列表 | 删除数据 |
| --- | --- | --- | --- |
| `pending` | 展示 | 不展示 | 不删除 |
| `executing` | 展示 | 不展示 | 不删除 |
| `completed` | 隐藏 | 展示 | 不删除 |
| `cancelled` | 隐藏 | 展示 | 不删除 |
| `superseded` | 隐藏 | 展示 | 不删除 |
| `rejected` | 隐藏 | 展示 | 不删除 |

## 9. 建议的实施阶段

### 阶段 A：展示字段补齐

- 增加申请人昵称/邮箱字段。
- 增加目标摘要字段。
- 增加阶段摘要字段。
- 增加 `can_review` 和 `can_cancel`。

### 阶段 B：前端三视图

- “待我审批”
- “我发起的”
- “历史记录”

### 阶段 C：状态中文化和进度展示

- 完成所有状态映射。
- 删除申请展示四阶段进度。
- 保留期显示预计完成时间。

### 阶段 D：历史数据治理

- 继续使用现有 `superseded` 标记。
- 对 pending + hidden 的历史申请执行状态修复。
- 对已完成但未收敛的申请执行状态聚合。
- 不物理删除任何历史申请。

### 阶段 E：回归和验收

- 新用户提交删除申请。
- 管理员在“待我审批”中看到并审批。
- 申请人看到状态从 pending 到 executing。
- `superseded` 不出现在默认列表。
- `cancelled` 只在历史中展示。
- 申请人不再以 UUID 作为标题。

## 10. 验收标准

### 10.1 审批

- 管理员能看到 pending 申请。
- 有权限的用户能通过或拒绝。
- 无权限用户看不到待审批列表。
- `pending=0` 时显示正常空状态。

### 10.2 展示

- 用户昵称优先，UUID 只作为兜底。
- 删除申请展示消息摘要和会话上下文。
- `executing` 展示阶段进度。
- 历史终态默认进入历史记录。

### 10.3 数据

- `superseded` 记录保留。
- `cancelled` 记录保留。
- 同一消息只有一条有效申请。
- 不出现 pending 但消息已隐藏而不收敛的申请。
