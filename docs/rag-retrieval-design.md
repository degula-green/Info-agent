# RAG 检索设计

> 状态：实现基线。三类入口、权限前置过滤、混合召回、RRF、可选重排和 AI 最终权限复核已在 `services/rag` 落地；服务一授权和模块二内容接口通过 HTTP 适配器对接。

## 1. 检索入口

系统主要有三个检索入口，入口不同，检索策略不同：

| 入口 | 用途 | 默认策略 | 输出 |
|---|---|---|---|
| AI 文档 | 用户提问，由知识库内容辅助大模型回答 | 混合检索，召回后组装受限上下文 | 已授权 chunk、引用和提示词上下文 |
| 全局搜索栏 | 在所有可见知识中搜索 | BM25 + kNN 混合检索 | 排序后的搜索结果和引用信息 |
| 知识库搜索栏 | 搜索某个指定知识库 | 全文 BM25 检索 | 搜索结果和高亮信息 |

知识库搜索栏的规则：

- 前端传 `knowledge_base_id` 时，只在指定知识库内执行全文检索。
- 未传 `knowledge_base_id` 时，在当前用户可见的全部知识库内执行全文检索。
- 知识库搜索栏不调用向量模型、不执行 Rerank，也不调用大模型。
- 附件只有元数据权限时，可以检索文件名等元数据，但不能把附件正文作为结果或 AI 上下文。

AI 文档和全局搜索均可以同时查询展示索引和受保护索引，但受保护内容必须先经过服务一的授权范围过滤。RAG 不直接连接或调用 OpenFGA。

## 2. 混合检索主流程

```text
请求校验
→ 本地解析查询意图和过滤条件
→ 并行准备 Embedding 与服务一授权范围
→ 展示索引/受保护索引执行 BM25、kNN
→ 批量权限复核
→ RRF 融合
→ 按知识对象去重和限额
→ 条件启用少量 Rerank
→ 返回最终候选
→ AI 文档入口构造受限上下文
```

### 2.1 服务一授权边界

**强制规则：RAG 服务不得安装 OpenFGA SDK、连接 OpenFGA 或自行执行权限判断。**

- OpenFGA 由服务一统一持有和管理，服务一是权限关系的唯一读写入口。
- 模块二通过服务一写入或撤销权限关系；RAG 只通过服务一读取授权结果。
- RAG 通过服务一的 `search-scope` 接口获取受保护索引所需的授权对象键。
- RAG 通过服务一的 `check-batch` 接口批量检查候选内容的 `view` 权限。
- 服务一返回稳定的资源对象键或授权快照，不向 RAG 暴露 OpenFGA Model、Tuple 或查询 DSL。

建议的内部接口：

```text
POST /internal/v1/authorization/search-scope
POST /internal/v1/authorization/check-batch
```

`search-scope` 返回的对象键用于 ES 的 `auth_object_key` `terms` 过滤；`check-batch` 用于 RRF 前的候选复核和交给大模型前的最终复核。授权请求必须携带用户、组织、调用服务、请求 ID 和追踪 ID。

RAG 目录只保留授权端口和服务一 HTTP 适配器：

```text
app/application/ports/authorization_gateway.py
app/infrastructure/service1/authorization_client.py
```

RAG 不得出现 `infrastructure/openfga/` 或其他直接访问 OpenFGA 的实现。

### 2.2 查询规划

优先使用本地规则解析查询：

- 文件名、项目编号、日期、金额、人员名等明确实体：BM25 权重更高，必要时跳过向量检索。
- “说明原因”“相关方案”等语义问题：BM25 和 kNN 并行执行。
- 默认不调用远程 LLM 做 Query Rewrite。
- 首轮召回不足时，最多触发一次改写；原问题和改写问题的向量应批量请求。

### 2.3 权限范围

展示索引：

```text
organization_id / owner_user_id / conversation_group_id 粗筛
→ BM25 + kNN
→ 按 auth_resource_type/id/part 批量 Check(view)
```

受保护索引：

```text
调用服务一 search-scope（服务一内部执行 ListObjects(view)）
→ 得到 knowledge_original:*、attachment_content:* 对象集合
→ 使用 auth_object_key terms filter
→ BM25 + kNN
→ 批量 Check(view)
```

受保护索引禁止先全量召回再过滤权限。服务一授权接口不可用或授权集合为空时，受保护索引直接返回空结果，不能降级为无过滤查询。

授权集合可以短时缓存，但缓存键至少包含：

```text
user_id + organization_id + resource_part + ACL 版本 + 索引版本
```

### 2.4 Embedding

每次语义检索默认只请求一次向量：

```text
规范化问题 → text-embedding-v4 → 1536 维向量
```

向量可以按“规范化问题 + 模型版本”缓存。Embedding 失败时，搜索可以降级为 BM25；权限失败时不能降级为无权限检索。

### 2.5 ES 召回

展示索引和受保护索引按检索计划执行以下查询：

```text
展示索引 BM25
展示索引 kNN
受保护索引 BM25
受保护索引 kNN
```

使用 `_msearch` 或异步并行减少网络往返。实际只查询当前用户需要的索引。

建议初始参数：

```text
BM25 size：20～30
kNN k：20～30
num_candidates：通过压测确定，初始约为 k 的 2～4 倍
RRF 候选池：30～50
最终返回：6～10 条
```

查询要求：

- 权限和生命周期条件放在 `filter` 中，不参与相关性评分。
- kNN 权限条件必须放在 kNN 查询内部。
- 过滤 `lifecycle_status=active`、`rag_eligible=true` 和有效版本。
- 首轮不启用高亮。
- `_source` 只返回必要字段，排除 `embedding` 和临时字段。
- `track_total_hits=false`，不查询无用总数。

附件元数据可以被 BM25 检索，但 `rag_eligible=false` 的元数据记录不能进入向量召回或 AI 上下文。

### 2.6 权限复核、RRF 和去重

权限复核应在 RRF 之前完成，避免无权限结果影响排名。RRF 只负责合并已授权的 BM25 和向量结果，不负责权限判断。

融合后按知识对象聚合，避免同一文件或消息的多个 chunk 占满结果：

```text
knowledge_item_id / attachment_id 分组
每个知识对象最多保留 2～3 个 chunk
```

展示版本和受保护原文版本可能同时命中，需要使用稳定的逻辑内容标识去重，不能只依赖 `chunk_id`。受保护版本仅在用户具备 `view` 权限时进入最终结果和 AI 上下文。

### 2.7 Rerank

Rerank 不作为默认步骤：

- 只对 RRF 后的前 8～12 条执行。
- 仅用于语义问题、结果分数接近或首轮置信度不足的情况。
- 远程 Rerank 必须设置严格超时。
- Rerank 失败直接使用 RRF 结果，不阻塞搜索。

## 3. 三个入口的处理方式

### 3.1 AI 文档

```text
用户问题
→ 查询规划
→ 混合检索
→ 权限复核
→ 选取少量高质量 chunk
→ 批量获取引用信息
→ 通过服务一执行最终权限检查
→ 组装受限提示词
→ 流式调用大模型
```

AI 文档入口只向大模型提供已经完成权限检查的内容，并设置 chunk 数量和上下文 token 上限。不能把 RRF 候选池或未经复核的 ES 内容全部拼入提示词。

知识库内容回源和引用信息必须批量获取，禁止对每个结果单独访问模块二数据库，避免 N+1 查询。

### 3.2 全局搜索栏

```text
用户查询
→ 解析过滤条件
→ 展示索引和有权限的受保护索引混合召回
→ 批量权限复核
→ RRF、去重、可选 Rerank
→ 返回搜索结果
```

全局搜索默认覆盖当前组织和用户可见的全部知识库。结果中可以包含文件名、标题、发送人、时间和来源定位等引用信息；正文返回仍受 `view` 权限约束。

### 3.3 知识库搜索栏

```text
用户查询 + 可选 knowledge_base_id
→ 构造知识库范围过滤
→ BM25 全文检索
→ 批量权限复核
→ 高亮最终结果
```

传入 `knowledge_base_id` 时，必须将其作为精确过滤条件。未传时查询全部可见知识库。该入口不做 kNN、RRF、Rerank 或大模型调用，适合文件名、标题、编号和原文关键词查找。

## 4. 性能目标和降级

建议先按以下预算进行压测，实际目标以远端 ES、Embedding 和服务一授权接口的基准结果为准：

```text
查询解析：< 10ms
Embedding：100～300ms
服务一授权：缓存命中 < 20ms，未命中为几十到数百毫秒
ES 召回：100～300ms
RRF/去重：< 20ms
```

建议目标：

```text
无 Rerank：P95 < 1.5 秒
启用 Rerank：P95 < 2.2 秒
```

降级原则：

- Query Rewrite 超时：继续使用原问题。
- Embedding 超时：全局搜索和 AI 文档可降级为 BM25；知识库搜索本来就只使用 BM25。
- Rerank 超时：使用 RRF 结果。
- 服务一授权接口超时或失败：受保护索引返回空结果，不能放宽过滤条件。
- 每个阶段记录独立耗时、候选数、权限过滤数和降级原因。

## 5. 相对旧项目的主要优化

| 旧问题 | 本方案 |
|---|---|
| 最多 3 个改写问题 | 默认不改写，最多一次补偿改写 |
| 每个问题单独 Embedding | 默认一次，改写时批量请求 |
| BM25、kNN 串行 | `_msearch` 或异步并行 |
| 每路召回 100 条 | 每路先取 20～30 条 |
| Rerank 最多 50 条 | 只重排 8～12 条 |
| 首轮多字段高亮 | 最终结果再补高亮 |
| 权限检查分散在结果处理后 | 受保护索引查询前过滤，命中后批量复核 |
| QA 逐条回源 | 批量获取引用和内容 |

旧项目的多轮串行方式是召回耗时接近 5 秒的主要原因。V3 的主路径应保持一次查询、一次向量化、一次并行 ES 召回；改写和 Rerank 只能作为受控的条件分支。

## 6. 实现前需要确定

1. AI 文档入口是否默认搜索全部可见知识库，还是由前端传入知识库范围。
2. 展示版本和受保护原文版本的逻辑去重字段，避免同一知识重复进入候选。
3. 远程 Rerank 服务的超时和是否允许首期默认关闭。
4. 以 P95 延迟还是首字节时间作为 AI 文档入口的主要验收指标。
