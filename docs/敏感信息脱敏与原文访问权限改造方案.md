# 敏感信息脱敏与原文访问权限改造方案

- 文档状态：实施中
- 创建日期：2026-10-04
- 最近修订：2026-10-04
- 适用范围：Core、Knowledge、RAG
- 目标：敏感信息默认脱敏；非来源群成员只能查看脱敏信息；原文查看和下载必须经过来源群成员关系或显式审批授权。

## 1. 背景

当前系统中已经存在以下能力骨架：

- Knowledge 保存消息原文和展示内容。
- Knowledge 计算 `content_visibility`、`original_access_required`、`sensitivity` 等字段。
- RAG 区分 display 和 protected 两套内容。
- Core/OpenFGA 定义了 `knowledge_item`、`knowledge_original`、`attachment_meta`、`attachment_content` 等资源关系。

但实际链路尚未闭环，存在以下问题：

1. 敏感信息识别规则过窄，容易漏判中文、无分隔符、仅有账号上下文、跨消息组合等场景。
2. 漏判后消息会被当成普通内容处理，原文直接成为 display 内容。
3. Knowledge 的普通列表、会话详情和消息接口主要按组织成员身份放行，没有对每条原文资源执行来源群和 OpenFGA 判断。
4. RAG display 索引可能直接包含漏判原文，导致组织内非来源群成员也能检索到明文。
5. OpenFGA 虽然定义了原文和附件内容关系，但当前没有完整的“审批通过后写入 viewer/downloader”链路。
6. Core 的 `iam.access_requests` 表存在，但尚无完整的申请、审批和 OpenFGA 同步实现。

本方案的目标不是只修补若干正则，而是把敏感判断、脱敏、存储、检索和权限控制拆成互相兜底的完整链路。

## 2. 核心原则

### 2.1 敏感识别不是安全边界

敏感识别负责决定展示哪一份内容，权限系统负责决定谁能访问原始内容。两者必须同时存在：

- 识别漏判时，权限仍应阻止非授权用户访问原文。
- 权限配置错误时，脱敏版本也不应包含原文。

### 2.2 默认失败关闭

以下情况必须按高风险管理，不得默认公开：

- 分类服务不可用
- LLM 超时、返回格式错误或置信度过低
- 规则命中冲突
- 附件无法完整解析
- 消息需要上下文才能判断
- 分类策略版本缺失

### 2.3 原文和展示内容硬分离

- 原文只进入受保护存储。
- `normalized_content` 只能保存经过分类和脱敏后的展示版本。
- `pending`、`failed`、`needs_review` 状态不得向普通业务接口返回正文。
- 列表、搜索、详情接口不得直接读取原文存储。

### 2.4 LLM 不能直接生成最终脱敏文本

LLM 只负责辅助判断和识别敏感片段：

- 输出风险等级
- 输出敏感 span
- 输出分类和置信度
- 输出判断依据

实际替换和脱敏由确定性代码完成。硬规则命中的内容不能被 LLM 降级为安全。

### 2.5 MVP 范围与边界

MVP 阶段只在组织群聊采集场景执行敏感分类和原文权限控制：

```text
knowledge_scope = organization
AND source_conversation_type = group
```

私人会话在 MVP 中按“私人信息 = 私聊内容”处理：

- 不调用敏感分类
- 不调用 LLM
- 不生成 protected 原文版本
- 保持 owner-only 访问
- `classification_required = false`

私人内容共享到组织时例外。共享动作会改变内容的访问范围，必须在共享发布前重新执行敏感分类，生成 display/protected 版本并进入组织权限链路。

## 3. 目标链路

```text
原始消息/附件
  -> 输入标准化
  -> 高召回规则检测
  -> 实体和结构化信息检测
  -> 单条与跨消息上下文判断
  -> 低置信度内容调用 LLM 辅助判断
  -> 生成结构化敏感决策
  -> 生成 span 级脱敏文本
  -> 二次复核脱敏结果
  -> display 内容发布
  -> 原文进入 protected 存储
  -> Core/OpenFGA 控制原文查看和下载
```

## 4. 敏感判定设计

### 4.1 输入标准化

检测前统一处理，但保留原文和原始偏移：

- 全角/半角转换
- 大小写归一化
- 繁简体归一化
- 空格、换行、制表符归一化
- 零宽字符和不可见字符清理
- HTML/XML/Markdown 解码
- JSON、YAML、SQL URI、连接串解析
- URL 编码、Unicode 转义、Base64 候选解码

归一化仅用于检测。脱敏时必须映射回原文范围，避免破坏原始消息。

### 4.2 规则检测

规则用于高召回识别明确或强上下文风险，不能只覆盖带 `=` 的英文格式。

至少覆盖：

- 密码：`密码`、`口令`、`password`、`passwd`、`pwd`
- 账号：`账号`、`账户`、`用户名`、`root`、`admin`、`administrator`
- 密钥：`secret`、`token`、`api key`、`access key`、AK/SK
- 身份信息：身份证、护照、手机号、邮箱
- 网络和基础设施：IP、域名、数据库地址、RDS、Redis、MySQL、PostgreSQL
- 认证材料：JWT、Bearer Token、PEM、私钥
- 连接串：`mysql://user:password@host`、JDBC、Redis URI

规则应覆盖无分隔符、中文分隔符、空格分隔、换行分隔和跨消息组合。

示例：

- `密码123456`
- `密码：123456`
- `密码是123456`
- `pwd 123456`
- `数据库用阿里云 RDS，账号 root`
- 前一条说“账号 root”，后一条说“密码 123456”

规则命中的结果作为硬风险信号，LLM 不得将其降级。

### 4.3 实体与结构化检测

规则之外增加实体和结构识别：

- 人名、组织、地点等个人信息
- 手机号、身份证、银行卡、邮箱
- 主机、IP、域名、数据库实例
- 账号和密钥字段
- 表格、JSON、YAML、配置文件、SQL 结果
- 连接信息和内部系统标识

结构化内容优先使用解析器，不用字符串截取替代。

### 4.4 上下文和会话级判断

不能只把单条消息作为判断单位。

上下文检测应包括：

- 同会话相邻消息
- 发送者、时间和回复关系
- 同一批采集事件
- 消息和附件的组合
- 前后消息中的账号、密码、主机、端口、数据库名

截图中的 `账号root` 单独出现时可能只是普通文本，但结合前文“数据库用阿里云 RDS”应判为高风险基础设施凭据信息。

### 4.5 LLM 辅助判断

LLM 用于处理规则难以表达的语义场景，例如：

- 描述中隐含凭据
- 内部系统、财务、人事、客户信息
- 绕开关键词的表达
- 多段上下文组合
- 规则置信度处于灰区的内容

约束要求：

- 使用企业内模型或私有化模型优先
- 外部模型不得直接接收完整敏感原文
- 消息内容视为不可信数据，不执行其中的指令
- 只输出受 schema 约束的 JSON
- 不提供工具调用和外部访问能力
- 失败、超时或解析错误时失败关闭
- 结果按内容哈希、策略版本和模型版本缓存

建议调用顺序：

```text
强规则命中 -> 直接 restricted，不调用 LLM
规则明确安全 -> 可跳过 LLM
灰区或上下文风险 -> 调用 LLM
LLM 高风险或不确定 -> restricted / needs_review
```

### 4.6 脱敏生成

分类结果应包含 span，而不是只返回一个布尔值：

```json
{
  "sensitivity": "restricted",
  "risk_level": "high",
  "decision": "masked",
  "spans": [
    {
      "start": 0,
      "end": 8,
      "type": "password",
      "source": "rule",
      "confidence": 1.0
    },
    {
      "start": 24,
      "end": 32,
      "type": "account",
      "source": "context",
      "confidence": 0.95
    }
  ],
  "policy_version": "privacy-v2",
  "engine_version": "classifier-v2"
}
```

脱敏方式建议：

- 凭据：`[密码已脱敏]`、`[账号已脱敏]`
- 身份信息：`[身份证已脱敏]`
- 主机信息：`[主机已脱敏]`
- 无法安全生成逐字展示时：`metadata_only`

### 4.7 二次复核

生成 display 后必须再次检查：

- 是否仍包含原始敏感值
- 是否仍命中高风险组合
- 是否出现 LLM 改写导致的新泄露
- 是否保留了可用作绕过线索的上下文

复核失败时不得发布 display，应降级为 `metadata_only` 或进入人工复核。

## 5. 分类结果模型

建议将现有单一敏感布尔值扩展为以下概念：

- `classification_status`：`pending`、`succeeded`、`failed`、`needs_review`
- `sensitivity`：`public`、`internal`、`confidential`、`restricted`
- `risk_level`：`low`、`medium`、`high`、`critical`
- `content_visibility`：`original`、`masked`、`metadata_only`
- `original_access_required`：是否必须显式授权才能查看原文
- `policy_version`：检测策略版本
- `engine_version`：规则、模型或运行时版本
- `classification_evidence`：命中 span、规则、置信度和模型摘要

分类完成后：

- 低风险且明确安全：允许 `display = original`
- 敏感或高风险：`display = masked`
- 无法确认安全：`display = metadata_only` 或人工复核
- 分类失败：不得发布正文

## 6. 存储与接口改造

### 6.1 原文存储

- 原文继续保存在受保护存储中。
- 原文存储必须启用基础设施加密，并优先增加应用层或列级加密。
- 加密密钥需要支持轮换，密钥访问和原文访问必须使用最小权限。
- 只有 Knowledge 内部受控服务和原文授权链路可以读取。
- 普通列表、搜索、详情接口不得直接查询原文表。

### 6.2 展示内容

- `normalized_content` 只保存 display 版本。
- `content_visibility` 必须与 display 内容一致。
- `pending`、`failed`、`needs_review` 状态不返回正文。
- display 版本必须可追溯到策略版本和分类记录。
- 原文、原始 payload、存储引用和私密内容字段不得出现在公共 JSON DTO 中。
- 内部持久化模型、内部 RAG 契约和用户接口 DTO 必须使用不同结构体。
- 原文字段可以额外使用 `json:"-"` 兜底，但不能以 `json:"-"` 代替结构体隔离。

### 6.3 对外接口

Knowledge 和 RAG 的公共接口应遵循：

- 列表和搜索只读 display。
- 原文读取使用独立接口。
- 原文接口必须通过 Core/OpenFGA。
- 下载使用独立资源和独立 action。
- 前端不得承担脱敏职责。
- 接口不得根据客户端传来的 `sensitive=false` 直接放行。
- `content` 字段继续保留，但其语义固定为 display 内容。
- 新增字段必须向后兼容，例如 `content_visibility` 和 `original_access_status`。
- 原文接口和公开 display 接口分别使用独立 DTO，避免公共序列化意外包含原文。

### 6.4 批量权限与避免 N+1

普通列表和搜索不逐条检查原文权限：

- display 内容只依赖组织 scope，不按消息逐条调用 OpenFGA。
- 原文详情按资源执行精确检查。
- 一页多条原文详情、导出和批量下载使用 Core `check-batch`，每批最多 100 条。
- RAG protected 检索使用 Core 返回的 authorized object keys 批量过滤。
- 使用短期 authorization scope 快照，缓存维度包含用户、组织、成员版本和 ACL 版本。
- 组织成员、群成员、申请授权或 ACL 版本变化时，旧快照立即失效。
- 禁止在列表渲染循环中逐条调用 OpenFGA。

### 6.5 历史敏感配置补做处理

MVP 不做历史数据全量迁移，但历史组织群聊中的敏感配置需要补做处理。

处理范围：

- `knowledge_scope = organization`
- `source_conversation_type = group`
- 历史消息中疑似包含密码、账号、数据库、主机、Token、连接串等敏感配置
- 私人会话默认不进入本批次，除非后续被共享到组织

处理方式：

1. 先对历史组织群聊消息执行 shadow classification，只产出结果和审计报告，不直接修改线上展示内容。
2. 按会话、时间窗口和风险等级分批分类，优先处理高风险群聊和最近消息。
3. 对确认敏感的消息生成脱敏 display，原文保留在 protected 存储。
4. 重新计算 content version 和 ACL version。
5. 更新或重建 RAG display 和 protected 索引。
6. 每批处理完成后执行抽样复核和明文残留检测。

处理要求：

- 任务必须幂等，可重试，可暂停。
- 处理过程不能影响新消息分类。
- 每次处理必须记录策略版本、模型版本、批次 ID 和结果。
- 分类处理失败的消息不得发布新 display，继续保留旧展示时必须有明确风险标记。
- 历史任务增加回滚能力，但“安全回滚”不得恢复明文展示。
- 如果 ES 需要重建，使用索引别名切换；旧索引快照只在安全恢复窗口内保留。

必须产出以下实施物料：

- 历史数据筛选 SQL 或扫描任务
- 分批处理任务和重试策略
- 结果审计报告
- 索引重建和别名切换方案
- 失败批次回滚和重跑方案
- 处理前后敏感样本对比

## 7. OpenFGA 与审批链路

### 7.1 资源关系

继续保持展示和原文分离：

- `knowledge_item.view`：负责脱敏展示内容
- `knowledge_original.view`：负责消息原文
- `attachment_meta.view`：负责附件元数据
- `attachment_content.view/download`：负责附件内容和下载

### 7.2 来源群成员

来源群成员应获得原文访问能力：

- 将已映射的群成员写入 `knowledge_original.viewer`
- 附件根据权限分别写入 `viewer` 和 `downloader`
- 只加入 `conversation_group.participant` 不足以访问原文

### 7.3 非来源群成员

非来源群成员默认只能查看 display：

- 组织成员身份只提供脱敏内容访问，不自动获得原文
- 原文查看和下载必须申请
- 必须校验申请人属于资源所在组织

### 7.4 审批和授权

审批通过后，Core 必须写入显式 OpenFGA 关系：

```text
user:<user_id> viewer knowledge_original:<knowledge_item_id>
user:<user_id> viewer attachment_content:<attachment_id>
user:<user_id> downloader attachment_content:<attachment_id>
```

审批要求：

- 审批人可为信息采集者、信息管理员或管理员
- 申请人不能审批自己的请求
- 查看和下载分别申请、分别授权
- 临时查看授权默认有效期建议为 7 天，可由组织策略配置
- 临时下载授权默认有效期建议为 24 小时或单次下载，可由组织策略配置
- 长期授权必须由管理员显式授予并记录审批依据
- 过期或撤销后删除 OpenFGA 关系并递增 ACL 版本
- OpenFGA 同步失败时授权状态保持 pending，不得只依赖数据库 approved 状态
- 所有申请、审批、授权和撤销写入审计日志

审计日志至少记录：

- 用户 ID、组织 ID、资源 ID、资源版本和 ACL 版本
- 动作：查看原文、查看附件、下载附件
- 内容版本：display 或 protected
- 结果：allowed、denied、approval_required、expired
- 申请 ID、审批 ID、审批人和审批依据
- 请求 ID、trace ID、策略版本和时间
- 原文访问日志不得保存原文正文

下载水印作为后续增强项。水印用于追溯下载来源，但不能替代查看和下载权限分离。

## 8. 分阶段落地

### 阶段 0：紧急收口

目标：先消除明文直接暴露路径。

- 把敏感分类限定为组织群聊，私人会话标记为 `not_required`
- 私人内容共享到组织时重新进入分类链路
- 普通接口在分类未完成时不得返回正文。
- 分类失败默认按 `restricted` 或 `metadata_only` 处理。
- 扩展高召回规则，覆盖截图中的中文和无分隔符写法。
- 增加数据库和账号组合上下文规则。
- 修复列表、详情和搜索只读 display 的边界。
- 公共 DTO 中禁止出现原文、原始 payload 和存储引用。
- 原文访问接口接入 Core/OpenFGA。
- 查看和下载使用独立权限。
- 原文访问、拒绝、审批和撤销写入审计日志。
- 列表和搜索消除逐条 OpenFGA 查询。
- 增加针对明文泄露的回归测试。

### 阶段 1：检测框架

目标：把单一 `privacy.Scan` 改造成可扩展分类框架。

- 增加标准化层
- 增加规则和实体检测
- 增加跨消息上下文
- 增加 span 级脱敏
- 增加脱敏后复核
- 增加分类状态、风险等级、策略版本和审计记录
- 增加原文存储加密和密钥轮换设计
- 增加授权有效期、撤销和 ACL 版本失效机制

### 阶段 2：LLM 语义补充

目标：处理规则难以覆盖的语义和上下文场景。

- 只在灰区、上下文风险或规则未覆盖场景调用 LLM
- 使用结构化 JSON 输出
- 结果不能覆盖硬规则
- 失败时失败关闭
- 建立评测集和成本、延迟、准确率监控
- 只对组织群聊的灰区内容启用 LLM
- 私人会话不调用 LLM

### 阶段 3：附件与历史敏感配置处理

目标：覆盖附件和历史组织群聊中的敏感配置。

- 文档、表格、PDF、图片 OCR
- 压缩包和嵌套附件
- 解析失败按高风险处理
- 对历史组织群聊消息执行分批 shadow classification
- 对确认敏感的配置生成脱敏 display 并保护原文
- 规则或模型升级后重新分类相关历史消息
- 递增 content version 和 ACL version
- 重建 display 和 protected 检索索引
- 支持分批暂停、重试、审计和索引别名回滚

## 9. 验收标准

### 9.1 安全验收

- 非来源群成员无法读取原文。
- 分类失败时无法读取正文。
- RAG 普通搜索不返回原文。
- 原文、附件查看和附件下载分别受 OpenFGA 控制。
- 审批过期或撤销后立即失效。
- 原文查看、附件下载、审批、授权和撤销均可审计。
- 任何普通接口都不直接读取原文存储。
- 公共 JSON 序列化结果不包含原文和相关存储字段。

### 9.2 识别验收

- `密码123456` 可识别
- `密码：123456` 可识别
- `账号root` 结合数据库上下文可识别
- 跨消息账号和密码组合可识别
- 全角、空格、换行、大小写变体可识别
- Base64、JSON、YAML、连接串可识别
- 截图和附件中的敏感信息可识别
- 规则命中不会被 LLM 降级

### 9.3 稳定性验收

- 分类服务失败时系统保持安全状态
- 重复处理幂等
- 策略升级可重放
- display 和 protected 索引版本一致
- 每次分类和访问均有审计记录

### 9.4 性能与兼容验收

- 列表和搜索不产生逐条 OpenFGA 检查。
- 100 条原文批量检查使用 `check-batch`，并验证 P95 延迟。
- 规则分类、灰区 LLM 分类、分类吞吐和失败率有监控指标。
- 审批通过后授权生效延迟和撤销后失效延迟有明确上限。
- 私人会话不进入分类队列。
- 历史敏感配置分批处理不影响新消息实时分类。
- `content` 字段继续返回 display 内容，旧前端可正常读取。
- 新增字段均为可选或带默认值，不破坏旧接口契约。

性能测试场景至少包括：

- 组织群聊列表 100 条和 500 条结果
- 跨知识库搜索命中 100 条和 500 条结果
- 原文详情单条检查
- 原文详情批量检查 100 条
- 搜索命中后 protected 索引过滤
- 规则分类吞吐和 LLM 灰区请求吞吐
- 分类服务超时、限流和失败关闭
- 历史敏感配置批处理期间的新消息实时链路
- 审批通过后授权生效时间
- 授权撤销和过期后的权限失效时间

性能指标先测量当前基线，再结合部署资源确定 SLO。所有指标必须区分规则分类和 LLM 分类，不能用一个平均延迟掩盖灰区请求的长尾。

## 10. 主要风险

1. 误报率上升，导致大量内容被脱敏。
2. LLM 成本和延迟增加。
3. 历史敏感配置补做处理需要任务窗口和索引重建窗口。
4. 附件解析覆盖不足，可能遗漏图片或嵌套文件。
5. OpenFGA 审批授权链路尚未实现，需要 Core、Knowledge 联合改造。
6. 如果使用外部模型，存在数据出境和供应链风险。
7. 私人内容共享到组织时如果未重新分类，会绕过组织群聊敏感链路。

## 11. 待审批决策

建议审批以下事项：

1. 是否采用“规则高召回 + 实体/上下文检测 + LLM 补充 + 确定性脱敏”的混合方案。
2. 是否接受“分类失败或不确定时默认脱敏或仅返回元数据”。
3. 是否允许 LLM 只输出结构化判断和 span，不允许直接生成最终正文。
4. 是否使用企业内或私有化 LLM。
5. 来源群成员是否默认获得原文查看权限。
6. 非来源群成员的查看和下载授权是否默认带有效期。
7. 是否在本期一并实现 Core/OpenFGA 的申请、审批、授权和撤销链路。
8. 历史组织群聊敏感配置补做处理的批次窗口、索引重建和回滚策略。
9. 下载水印是否列入后续版本。

## 12. 建议结论

建议采用“都做，但分主次”的方案：

- 规则和实体检测作为第一层高召回防线。
- 上下文和会话级检测作为第二层。
- LLM 作为第三层语义补充，不做唯一判断依据。
- 脱敏由确定性代码执行，LLM 不直接改写最终正文。
- 原文访问始终由 OpenFGA 控制。
- 敏感分类只适用于组织群聊，私人会话 MVP 不分类。
- 私人内容共享到组织时必须重新分类。
- 历史组织群聊中的敏感配置补做分批分类和索引重建。
- 原文查看、下载、审批、授权、撤销和过期全部审计。
- 原文存储加密，公共 DTO 不包含原文。
- 分类失败、模型失败和无法确认安全时失败关闭。

只改正则无法覆盖语义和上下文；只上 LLM 无法保证稳定性、成本和数据安全。两者结合，并配合原文隔离、确定性脱敏和 OpenFGA 审批授权，才能形成完整闭环。
