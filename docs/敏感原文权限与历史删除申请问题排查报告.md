- 排查方式：只读检查代码、数据库诊断结果、远端 OpenFGA 模型和 tuples

## 1. 排查结论摘要

本轮定位到三个相互关联但需要分开处理的问题：

1. **管理员和信息管理员看不到敏感原文的直接原因已经确认。**
   `knowledge_item` 上有 `moderator` 关系，但 `knowledge_original.view` 的授权表达式只允许原文 Owner 或显式 `viewer`，没有继承 `moderator`。因此，组织管理员或信息管理员即使已经拥有组织级管理权限，也可能在原文接口的 OpenFGA 检查中被拒绝。

2. **“外部群成员 + 组织成员”原文权限的设计意图存在，但当前资源上的实际权限事实不完整。**
   当前同步链路会把参与者列表作为 `original_viewer_user_ids` 传给 Core，但抽查的知识资源只有原文的 `parent` tuple，没有发现参与者对应的 `viewer` tuple。说明至少存在权限同步未执行、参与者映射为空/过期、同步到了其他资源或使用了不同授权模型等情况，不能仅凭数据库中的群成员记录放行原文。

3. **历史删除申请不消失、重复申请仍显示和删除状态不收敛，分别有明确的实现缺口。**
   - 申请列表的 `mine` 查询没有排除已完成、已失效或重复记录，也没有按消息资源聚合。
   - 数据库唯一约束只覆盖“申请人 + 幂等 key”，不能阻止同一消息使用不同 key 或由不同用户重复创建申请。
   - 删除隐藏阶段写入了 `knowledge.deletion.requested`，但 outbox 发布器只读取和标记 `knowledge.ready`，删除事件不会被发布给 RAG。
   - RAG 即使收到删除事件，目前也只删除向量和 chunk，没有回写 Knowledge 的删除阶段、对象存储状态或 OpenFGA 权限撤销结果。因此已有记录停在 `executing/deleting` 是预期的代码结果，不是前端刷新问题。

## 2. 用户期望的权限规则

本报告按下面的规则判断现状是否正确：

| 用户身份 | 组织内 | 目标外部群成员 | 敏感原文 | 删除组织群消息 |
| --- | --- | --- | --- | --- |
| 外部群成员且已映射为组织用户 | 是 | 是 | 允许 | 按组织删除权限判断 |
| 组织成员但不在目标外部群 | 是 | 否 | 不允许，需申请授权 | 普通成员只能申请 |
| 外部群成员但无法映射为组织用户 | 无法确认 | 是 | 不允许 | 不允许 |
| 普通组织成员 | 是 | 任意 | 无群成员资格时不允许，需申请 | 只能发起申请 |
| 组织 Owner/管理员 | 是 | 不要求 | 允许 | 可直接删除 |
| 信息管理员 | 是 | 不要求 | 允许 | 可直接删除 |
| 已批准的临时授权用户 | 按授权记录 | 不作为群成员判断依据 | 在授权有效期内允许 | 不自动获得删除权限 |

这里的“外部群成员”必须是目标群的参与者，同时通过内部身份映射成为当前组织的 active member。只有组织成员或只有外部群成员，均不能单独构成敏感原文访问资格。

## 4. 问题一：管理员和采集者无法查看敏感原文

### 4.1 OpenFGA 模型的直接原因

当前模型 `services/core/config/openfga/model.fga` 的关键关系为：

```fga
type knowledge_item
  relations
    define moderator: information_admin from organization
    define view: owner or member from organization or member from conversation_group
    define delete: owner or moderator

type knowledge_original
  relations
    define parent: [knowledge_item]
    define owner: [user]
    define viewer: [user]
    define eligible_viewer: owner or viewer
    define view: eligible_viewer and view from parent
```

`moderator` 只参与了 `knowledge_item.delete`。`knowledge_original.view` 的 `eligible_viewer` 没有 `moderator from parent`，因此：

- Owner 或显式 `viewer` 可以继续参与原文检查；
- `information_admin`/Owner 角色虽然可以成为 `knowledge_item.moderator`，但不会因此成为 `knowledge_original.eligible_viewer`；
- `GetKnowledgeOriginal` 最终检查的是 `knowledge_item` 的 `original` 资源部分，Core 再映射到 `knowledge_original`，所以不会自动沿用删除权限。

代码位置：

- 模型：`services/core/config/openfga/model.fga:18-34`
- 原文访问：`services/knowledge/internal/service/service.go:3061-3125`
- Core 原文资源映射：`services/core/internal/httpapi/authorization_handler.go:130-151`

这解释了“管理员账号仍是采集者、也在外部群里，但看不到原文”：采集者/群成员 tuple 只能解决参与者路径，管理员关系缺失时仍会失败；而且当前抽查资源本身已经处于删除态。

### 4.2 群成员路径的实际事实不完整

当前权限同步代码确实尝试将参与者传入原文 viewer：

```go
originalViewers := append([]string(nil), participantUserIDs...)
...
"original_viewer_user_ids": originalViewers,
```

代码位置：`services/knowledge/internal/coreclient/client.go:265-283`。

Core 侧会把这些用户写成：

```text
user:<participant>
viewer
knowledge_original:<knowledge_item_id>
```

代码位置：`services/core/internal/application/authorization.go:180-207`。

但是，对抽查资源实际读取到的原文关系只有：

```text
knowledge_item:ae6d2160-3c7f-427f-9098-111fd0fbcdf0
parent
knowledge_original:ae6d2160-3c7f-427f-9098-111fd0fbcdf0
```

没有发现 `lyc` 或群参与者对应的 `viewer` tuple。当前可以确认“资源权限事实不完整”，但在修改前还需通过权限同步日志、参与者映射结果和 ACL 版本确定具体是哪一环丢失：

1. 采集时没有拿到外部群参与者的内部用户 ID；
2. 外部用户映射到了错误的组织用户；
3. 权限同步没有执行或执行失败，但知识项仍被标记为 `permission_ready=true`；
4. 同步对象 ID 与当前知识项 ID 不一致；
5. 使用了未固定的 OpenFGA authorization model；
6. 历史 ACL 没有回填，当前 ACL 版本只是数据库状态，不代表远端 tuple 已完整。

### 4.3 不能直接把所有组织成员放进原文 viewer

当前 `knowledge_item.view` 含有 `member from organization`。如果将 `knowledge_original.eligible_viewer` 直接改成继承父资源的 `view`，会把所有组织成员都变成原文访问者，违反“组织内但不在外部群不能看原文”的要求。

后续应建立独立的原文资格关系，语义上至少要同时满足：

```text
conversation_group#participant
AND
organization#member
```

该群成员原文关系应与管理员/信息管理员原文关系分开表达，不能复用普通知识条目的展示权限。

### 4.4 OpenFGA 模型漂移风险

远端 Store 为：

```text
01M169MV47PBKEA2JHYQP62WZ0
```

基于远端 Store 的只读查询，当前共有 3 条 authorization model 记录，但可以归并为 2 个语义版本：

| 模型 ID | 版本特征 | 当前判断 |
| --- | --- | --- |
| `01M45MJAZWYAA3Z2P3FXJDR7ZH` | 最新；包含 `information_admin`、`moderator`、`delete` | 当前 latest，关系定义与仓库中的 `model.fga` 一致 |
| `01M45M88K1AQ8278WG1E633S8B` | 包含 `information_admin`、`moderator`、`delete` | 与 M45MJ 的关系定义完全相同，属于重复发布 |
| `01M2K93R412BZ42VT57QTPN3H7` | 没有 `information_admin`、`moderator`、`delete` | 旧模型，与当前删除和角色同步代码不兼容 |

M45M88 和 M45MJ 的 `type_definitions` 已做只读比较，结果完全一致，SHA-256 均为：

```text
FCC43278D5313ACE6709A2DE63C3C9BA8E51B8691B17072D0E5F725B93C43F2E
```

这说明至少发生过一次无变化重复发布。虽然当前两条模型的行为相同，但这种发布方式会让“latest”持续变化，并掩盖真正的模型变更。

需要注意：M45MJ 和 M45M88 虽然匹配当前仓库模型，但**并不是最终满足敏感原文规则的模型**。它们的 `knowledge_original.view` 仍然只允许 `owner` 或显式 `viewer`，没有继承管理员/信息管理员的 `moderator`，也没有表达“外部群参与者 AND active 组织成员”的原文访问资格。因此：

- 如果当前必须先稳定运行，可把 M45MJ 作为临时固定版本；
- 最终必须发布一份包含管理员原文权限和群成员原文资格的新模型，并固定新的 model ID；
- 不能把 M45MJ 视为敏感原文权限已经修正的版本。

#### 4.4.1 漂移为什么会发生

当前没有把 OpenFGA 模型 ID 固定到运行环境中。`services/core/.env` 和 `services/knowledge/.env` 中的 `CORE_OPENFGA_MODEL_ID` 仍是注释状态：

```text
# CORE_OPENFGA_MODEL_ID=
```

Core 配置的默认值也是空字符串：

```go
OpenFGAModelID: env("CORE_OPENFGA_MODEL_ID", ""),
```

代码位置：`services/core/internal/config/config.go:95`。

OpenFGA 客户端只在 model ID 非空时显式传入：

```go
if c.modelID != "" {
    body["authorization_model_id"] = c.modelID
}
```

代码位置：

- `services/core/internal/infrastructure/openfga/client.go:36`
- `services/core/internal/infrastructure/openfga/client.go:61`
- `services/core/internal/infrastructure/openfga/client.go:216`

当 model ID 为空时，OpenFGA 会自动使用 Store 中的 latest model。于是会出现以下漂移链：

1. 仓库中的 `model.fga` 只有代码作用，没有可追踪的自动发布机制；
2. 模型通过手工方式写入远端，每次写入都会生成一个不可变的新 model ID；
3. 即使模型定义完全一样，也会产生 M45M88、M45MJ 这类重复版本；
4. 运行时没有固定 model ID，`/check`、`/list-objects` 和 `/write` 会跟随 latest 自动切换；
5. 新模型发布后，代码可能没有同步发布、tuple 可能没有回填、旧检查可能仍在旧模型上执行；
6. 于是“代码模型”“远端 latest”“实际 tuple”三者可能分别处于不同阶段，造成同一用户在不同时间得到不同授权结果。

另外，OpenFGA 的历史模型是不可变记录。发布新模型不会覆盖旧模型，因此旧模型仍会保留在 Store 中。彻底解决漂移不能靠删除旧模型，而要靠运行时明确引用一个经过验证的固定 model ID。

#### 4.4.2 彻底治理方案

1. 以仓库中的 `services/core/config/openfga/model.fga` 作为唯一事实来源，所有关系变更都必须经过代码评审。
2. 模型变更必须和代码、tuple 回填迁移、权限矩阵测试放在同一个交付阶段中。
3. 发布模型后获取不可变 model ID，并写入环境变量或部署配置，例如 `CORE_OPENFGA_MODEL_ID=01M45MJAZWYAA3Z2P3FXJDR7ZH`。该值不能写 `latest`，也不能留空。
4. Core 启动时强制要求 model ID；缺失时直接启动失败，不能回退到 latest。
5. 启动和部署时校验固定 model ID 是否存在，以及关键关系是否与本版本代码兼容；校验失败时拒绝启动。
6. Check、ListObjects、Write、Delete 和 ACL 回填必须全部使用同一个固定 model ID，不能出现检查使用一个模型、回填使用 latest 的情况。
7. 没有权限语义变化时复用已有 model ID；每次部署都重新发布模型只会继续制造重复版本。
8. 按 expand/migrate/contract 顺序演进：先发布向后兼容的新模型，再回填关系，再切换运行时固定 ID，验证稳定后再清理旧权限路径。
9. 日志、审计和诊断结果记录实际使用的 model ID，便于定位环境间同一 tuple 结果不一致的问题。
10. 将远端模型盘点加入发布前检查，确认当前唯一活动版本、待回填的关系和是否存在无意义重复发布。

这属于独立的配置和发布流程缺口。修复权限前必须先确定、发布并固定一份模型 ID，验证当前代码和远端模型一致后，再执行 tuple 回填和权限验收。

### 6.2 当前幂等约束不能保证消息级幂等

迁移 `db/migrations/20261005_message_deletion_pipeline.up.sql:49-75` 只建立了：

```sql
UNIQUE (requester_user_id, idempotency_key)
```

这只能保证同一申请人重复提交同一个 key 时返回已有申请，不能防止：

- 同一用户为同一消息生成不同 key；
- 不同用户为同一消息创建重复申请；
- 两个不同请求在资源级没有唯一保护时并发插入；
- 老版本 key 和新版本 key 对同一消息形成多条历史记录。

前端目前使用 `message-delete:<messageID>:v<contentVersion>` 形式的 key，只能减少同一前端调用的重复，不能替代数据库的资源级约束。

后续需要在事务和数据库约束两个层面定义“同一资源只有一条有效删除流程”，例如按 `scope_type + scope_id` 建立有效状态唯一索引，或者增加规范主申请字段和合并关系。具体 SQL 设计要先处理历史重复数据，避免直接加约束失败。

### 6.3 个人主页继续显示旧申请的直接原因

前端个人主页 `apps/web/src/views/info/InfoProfilePage.vue:315-328` 在 `mine` 视图中调用：

```ts
listDeletionRequests(accessScope.value, accessScope.value === 'inbox' ? 'pending' : '')
```

因此 `mine` 视图传入空状态，含义是查询该用户的全部删除申请。Knowledge 侧：

- `services/knowledge/internal/service/service.go:3210-3246`
- `services/knowledge/internal/repository/postgres.go:3439-3490`

当前只按 requester、organization、status 和时间排序，没有：

- 以消息资源去重；
- 优先保留 `messages.delete_request_id` 指向的规范申请；
- 将重复申请标记为 `merged` 或 `superseded`；
- 隐藏已完成、已失效或资源已经不存在的历史申请；
- 将同一资源的多个申请聚合成一条可解释记录。

所以“原消息已经删除，但个人主页仍看到旧申请”是后端列表语义和前端展示语义共同造成的，不是单纯缓存未刷新。

### 6.4 删除状态停留在 executing/deleting 的直接原因

`HideDeletionTargets`（`services/knowledge/internal/repository/postgres.go:3523-3575`）会：

1. 把消息和知识项标记为 `deleting`；
2. 把删除目标标记为 `hidden`；
3. 写入 `knowledge.deletion.requested` outbox 事件。

但是，Postgres 和 Memory 实现的 `GetOutbox` 只筛选：

```text
event_type = 'knowledge.ready'
```

`MarkOutboxPublished` 和 `MarkOutboxFailed` 也只更新 `knowledge.ready`。因此删除事件虽然写入表中，却不会被 `PublishOutbox` 取出并发布到 Redis，RAG 删除消费者收不到事件。

代码位置：

- Postgres：`services/knowledge/internal/repository/postgres.go:3957-3990`
- Memory：`services/knowledge/internal/repository/memory.go:4131-4165`
- 发布调用：`services/knowledge/internal/service/service.go:2602`

### 6.5 即使发布事件，后续状态回写仍不完整

RAG 已注册 `knowledge.deletion.requested` 处理路径：

- `services/rag/app/application/runtime.py:60-65`
- `services/rag/app/application/deletion_service.py:19-49`

当前处理内容是删除 Elasticsearch 资源和 RAG PostgreSQL chunk，并返回删除数量。但没有发现：

- 回调 Knowledge 更新 `vector_state=deleted`；
- 更新 `object_state` 并调用对象存储删除；
- 更新 `auth_state` 并撤销 OpenFGA viewer/owner/access tuple；
- 计算所有阶段完成后将 `deletion_requests.status` 更新为 `completed`；
- 把不可重试错误和可重试错误写入 `last_error`；
- 处理多删除申请指向同一资源时的单一执行主流程。

所以当前状态卡住不是一个单点 bug。修复 outbox 后，还必须补齐“阶段回调 + 状态聚合 + 重试/失败”闭环，否则状态可能从 pending 前进到部分完成后再次卡住。

## 7. 修复前必须先确认的事项

为了避免再次误改权限或误删审计记录，建议开发前先完成以下只读核验：

1. 找一条仍为 `active/ready` 的敏感组织群消息，确认其 `knowledge_item_id`、`conversation_group_id`、组织 ID、敏感字段和 ACL 版本。
2. 核对该消息的外部群参与者列表，逐个核对外部身份到内部用户 ID 的映射结果和 active membership。
3. 对该资源执行 OpenFGA `check`，分别验证 `knowledge_item#view`、`knowledge_original#view`、`knowledge_item#delete`，记录使用的 authorization model ID。
4. 读取该 `knowledge_original` 的全部相关 tuples，确认是否有 parent、viewer、owner、moderator 推导链。
5. 核对 Knowledge 标记 `permission_ready=true` 时是否确实收到 Core 同步成功响应，不能只看数据库字段。
6. 备份删除申请、删除目标、删除审计和消息关联数据，再按消息资源统计重复申请，选出规范申请，不能直接物理删除历史记录。
7. 核对 outbox 中 `knowledge.deletion.requested` 的待发布数量、失败原因和重试次数，确认没有被旧 worker 永久忽略。
8. 先确认对象存储、RAG、Knowledge 和 Core 之间的删除回调契约，再实现状态推进，避免只删向量而数据库仍显示 executing。

## 8. 建议的后续实施阶段

以下阶段按依赖顺序排列。本报告只提出计划，不在本轮执行。

### 阶段 A：固定授权模型并修正原文权限语义

- 发布一份包含管理员原文权限和“群参与者 AND 组织成员”语义的 OpenFGA 模型。
- 固定 Core、Knowledge 使用的 authorization model ID，禁止运行时跟随默认最新模型漂移。
- 明确 `knowledge_original.view` 的组成：Owner、组织 Owner/信息管理员、有效临时授权、经过身份映射且同时属于目标外部群和组织的用户。
- 增加模型级测试，验证组织内非群成员不能看原文。

### 阶段 B：权限事实回填和管理员申请补偿

- 从可追溯的外部群成员和内部组织成员数据重建目标资源的参与者集合。
- 只对“外部群参与者 + active 组织成员”写入原文资格关系，不把全体组织成员写入 viewer。
- 对 Owner/信息管理员验证组织角色 tuple，并通过模型检查原文权限。
- 对当前已具备权限但仍为 pending 的原文申请做可审计的自动关闭/替代处理。
- 回填后重新计算 ACL 版本，并把 `permission_ready` 与远端同步结果绑定。

### 阶段 C：删除事件发布闭环

- 让 Knowledge outbox 同时读取 `knowledge.ready` 和 `knowledge.deletion.requested`。
- 让 published/failed 状态更新不再写死为 `knowledge.ready`。
- 补充事件类型、schema version、retry、dead-letter 和重复消费测试。
- 先恢复删除事件的可观测性，再恢复历史卡住任务，避免直接批量重放未知状态。

### 阶段 D：删除阶段回调和状态聚合

- RAG 删除向量和 chunk 后回调 Knowledge，回写 `vector_state` 和阶段结果。
- 增加对象存储删除 worker，按引用计数/共享对象引用确认后删除对象，回写 `object_state`。
- 增加 OpenFGA 关系撤销阶段，回写 `auth_state`；数据库生命周期状态始终优先拒绝访问。
- 由 Knowledge 聚合所有 target 阶段：全部成功为 `completed/deleted`，可重试失败进入重试，永久失败进入 `failed`，但保持不可见。
- 删除回调必须按 request/target/content version 幂等。

### 阶段 E：历史重复申请治理和查询语义

- 先导出并备份历史删除申请、目标和审计日志。
- 为每个消息选出一个规范删除流程，其他记录标记为 `merged`/`superseded` 或等价的非活动状态；是否保留原记录由审批决定。
- 对已完成、已替代、已拒绝且资源已消失的申请制定个人主页展示规则：默认只展示有效申请和最近一次最终结果，历史详情仍可审计查询。
- 增加资源级有效申请唯一约束和并发事务保护。
- 保留用户可理解的状态、申请人、消息摘要、删除原因和最终结果，不能用简单隐藏掩盖数据问题。

### 阶段 F：端到端回归和小批量恢复

- 先在测试资源上验证权限矩阵和删除状态机。
- 再小批量恢复历史删除事件，逐条观察 Knowledge、RAG、对象存储和 OpenFGA 的阶段状态。
- 最后处理历史数据补偿；任何物理删除前保留审计备份和回滚窗口。

| 操作 | 类型 | 是否需要审批 | 本轮是否执行 |

## 10. 验收矩阵

### 10.1 原文访问

| 场景 | 预期结果 |
| --- | --- |
| 外部群成员，已映射为 active 组织成员 | 可查看敏感原文 |
| 组织成员，但不在目标外部群 | 只能看脱敏内容；申请批准前不能看原文 |
| 外部群成员，但无法映射为内部用户 | 只能看脱敏内容或无权访问；不能因外部 ID 直接放行 |
| 组织 Owner/管理员，不在群内 | 可查看敏感原文 |
| 信息管理员，不在群内 | 可查看敏感原文 |
| 普通用户获得有效临时授权 | 授权有效期内可查看，过期后立即拒绝 |
| 权限服务不可用或 ACL 未完成 | 失败关闭，不能返回原文 |
| 消息为 deleting/deleted/purged | 一律不可查看原文 |

### 10.2 删除申请和状态

| 场景 | 预期结果 |
| --- | --- |
| 管理员直接删除 | 不创建 pending 申请，创建一条规范执行记录并立即隐藏 |
| 普通成员首次申请 | 创建一条 pending 申请 |
| 同一消息重复点击/并发提交 | 返回同一规范申请，不新增重复有效记录 |
| 不同用户申请同一消息 | 按产品策略合并到同一有效删除流程，不能并行重复执行 |
| 管理员已有遗留原文申请 | 权限补偿任务可审计地关闭或替代，不再要求重复申请 |
| 删除消息已隐藏但向量未清理 | 页面显示执行中，消息和原文不可见 |
| 向量、对象、权限全部清理完成 | request 与 target 状态收敛为 completed/deleted |
| 某阶段可重试失败 | 保持不可见，记录失败原因并自动重试 |
| 重复申请已合并 | 个人主页默认只显示规范记录，历史关联可审计查看 |
