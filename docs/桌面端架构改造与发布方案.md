# 桌面端架构改造与发布方案

- 文档状态：待评审
- 编写日期：2026-10-07
- 目标平台：Windows 优先，后续扩展 macOS
- 目标形态：Electron 桌面应用，本地前端资源，远端后端服务，本地 sidecar

## 1. 目标与范围

本方案定义 Info Agent 从 Web 产品演进为桌面端产品的完整路线，覆盖：

1. 现有 Web 前端到桌面前端的改造。
2. 服务端后端服务的部署边界。
3. 微信采集器和 form-browser 的本地 sidecar 化。
4. JEV 替换 Laya/intent 服务。
5. 远端 API、认证、域名和 HTTPS。
6. Windows 安装包、代码签名和自动更新。
7. 测试、灰度和正式发布流程。

本方案不包含：

- 具体业务功能的新增设计。
- 桌面端与 Web 端同时发布的双产品策略。
- macOS 首版发布，但架构需要为其保留扩展空间。

## 2. 已确定的产品决策

| 决策项 | 结论 |
| --- | --- |
| 桌面技术栈 | Electron |
| 前端形态 | 打包本地 `apps/web/dist`，不长期依赖远端 Web 页面 |
| 后端位置 | 部署在服务器 |
| 微信采集器 | 随桌面端启动，运行在客户端 |
| form-browser | 随桌面端启动，运行在客户端 |
| intent/laya | 不再部署和使用 |
| 意图理解 | 使用 JEV |
| 首版平台 | Windows x64 |
| 服务端 API | 默认使用公网 HTTPS 域名；桌面端不要求公司内网、VPN 或特殊网络 |

## 3. 当前状态

### 3.1 已有能力

- `apps/web`：Vue 3 + TypeScript + Vite，可生产构建。
- `services/core`：认证、组织、RBAC、OpenFGA 权限。
- `services/knowledge`：采集、会话、消息、附件、知识库、删除流程。
- `services/rag`：解析、向量化、检索、问答、删除回调。
- `services/agent`：任务规划、执行、审批、事件流。
- `services/collectors/wechat`：本机微信数据库采集。
- `services/form-browser`：Playwright 表单填写 sidecar。
- `gateway/nginx`：Web/API 路由。
- `docker/docker-compose.yml`：中间件和部分服务。

### 3.2 当前缺口

| 缺口 | 影响 |
| --- | --- |
| 没有 Electron 工程 | 无法构建和发布桌面安装包 |
| Web API 默认使用相对路径 | 本地静态包无法直接访问远端 API |
| Web 默认访问 `http://localhost:8091` | 桌面端需要安全的本地 sidecar 通道 |
| Knowledge 通过 URL 主动访问微信采集器 | 客户端本地服务无法被服务端直接访问 |
| Agent 通过 URL 主动访问 form-browser | form-browser 本地化后服务端无法直接访问 |
| Compose 没有 Agent 服务 | 服务端后端部署不完整 |
| Compose 包含本地采集器和表单浏览器 | 服务端和客户端部署边界混淆 |
| OAuth 回调使用 localhost | 生产认证和深链不可用 |
| 没有域名、TLS、代码签名和更新服务 | 无法安全分发正式桌面版本 |
| 意图服务仍存在 Laya 配置 | 部署链路和依赖冗余 |

## 4. 目标架构

### 4.1 总体结构

```text
Electron 主进程
  ├── 本地 Vue 静态资源（app:// 协议）
  ├── 桌面窗口和系统集成
  ├── 本地配置和 OS Keychain
  ├── 自动更新
  ├── WeChat Collector sidecar
  └── Form Browser sidecar
          |
          | HTTPS
          v
公网 HTTPS API 网关（企业内网部署为可选模式）
  ├── /api/core
  ├── /api/knowledge
  ├── /api/rag
  └── /api/agent
          |
          v
Core / Knowledge / RAG / Agent / Workers
          |
          v
PostgreSQL / Redis / MinIO / OpenFGA / Elasticsearch
```

| --- | --- | --- |
| Core Service | 是 | 认证、组织、权限 |
| Knowledge Service | 是 | 业务数据和设备配对 |
| RAG API | 是 | 检索和问答 |
| RAG Worker | 是 | 解析、索引、删除消费 |
| Agent API | 是 | 任务、审批、SSE |
| Agent Knowledge Worker | 是 | 消费 Knowledge 事件 |
| Agent Task Workers | 是 | 执行 Agent 任务 |
| PostgreSQL | 是 | 已有 |
| Redis | 是 | 已有 |
| MinIO | 是 | 已有 |
| OpenFGA | 是 | 已有 |
| Elasticsearch | 是 | 已有 |
| Form Browser | 否，客户端 | 用户本地浏览器状态 |
| WeChat Collector | 否，客户端 | 读取本机微信数据 |

| 组件 | 是否进程 | 说明 |
| --- | --- | --- |
| Electron 主进程 | 是 | 窗口、IPC、Sidecar、更新 |
| Electron Renderer | 是 | 本地 Vue 前端 |
| WeChat Collector | 是 | 本机微信采集 |
| Form Browser | 是 | 本机表单自动化 |

## 5. 关键架构修改

### 5.1 前端加载方式

从“远端 Web 页面”调整为：

```text
Electron 加载本地 apps/web/dist
```

建议使用自定义协议：

```text
app://info-agent/
```

不要直接长期使用 `file://`，原因是：

- `file://` 的 Origin 和行为不稳定。
- 无法可靠使用 CORS。
- 深链、Service Worker、缓存和 CSP 配置受限。
- 自定义协议更容易配置安全和更新策略。

### 5.2 API 地址

构建时不要写死服务器 IP。

建议增加运行时配置：

```json
{
  "apiBaseURL": "https://api.example.com",
  "updateURL": "https://update.example.com",
  "environment": "production"
}
```

默认方案是桌面端内置稳定的公网 HTTPS API 地址，用户只需要普通互联网连接，不需要配置公司内网、VPN、公网 IP 或端口映射。

可通过以下方式提供高级定制：

- 默认安装包内置公网 API 地址。
- 企业定制版可通过配置文件、MDM 或组策略写入内网地址。
- 环境变量仅用于开发和测试。

只有在企业私有化部署时，才允许把 API 地址切换为内网域名；这不是个人开发者版本的前置条件。

前端 API 配置对应：

```text
VITE_CORE_BASE_URL
VITE_KNOWLEDGE_BASE_URL
VITE_RAG_BASE_URL
VITE_AGENT_BASE_URL
```

微信采集器和 form-browser 属于本地 sidecar，不通过 `VITE_*` 或 Renderer 直接暴露地址；桌面端统一由 Electron Main Process 通过 IPC 和本地进程管理访问。

生产包只允许 HTTPS。

### 5.3 认证方案

桌面端不能依赖浏览器 Cookie 作为主要认证方式。

建议目标方案：

- Access Token 只保存在 Renderer 内存或 Main Process 内存。
- Refresh Token 保存在 OS Keychain/DPAPI。
- 设备密钥保存在 OS Keychain。
- Core 增加 native client refresh 接口。
- OAuth 使用系统浏览器或桌面深链回调。
- 所有 Token 刷新由 Main Process 统一处理。
- Renderer 不接触长期 Refresh Token。

建议桌面认证流程：

```text
启动
  -> Main 读取 Refresh Token
  -> 调用 Core 刷新 Access Token
  -> 注入短期 Access Token 给 Renderer
  -> Access Token 过期前自动刷新
  -> 退出登录时删除 Keychain 数据
```

如果首版继续使用远端 Web，Cookie 方案可以临时保留，但不作为长期桌面架构。

### 5.4 微信采集器控制流反转

当前 Knowledge 通过 `KNOWLEDGE_WECHAT_COLLECTOR_URL` 调用本机采集器。改为桌面端后，服务端不能访问客户端 `127.0.0.1`。

目标流程：

```text
Electron Main
  -> 启动/停止/监控 WeChat Collector
  -> 通过本地 IPC 获取状态

WeChat Collector
  -> 使用设备密钥签名
  -> 主动向 Knowledge 上报 discovery/messages/attachments/status

Knowledge
  -> 管理设备、配对、授权和业务状态
  -> 不直接调用客户端 localhost
```

网络要求固定为：

```text
用户桌面端 -> 普通互联网 -> 公网 Knowledge API
```

用户不需要加入公司内网，也不需要配置 VPN。只有目标网站自身要求内网或 VPN 时，才由用户自己的网络环境决定是否可访问。

需要改造：

- 废弃服务端到采集器的 `WechatCollector()` 直接调用。
- 保留并强化 device pairing。
- 将 stop、status、contacts、conversations 等操作改为客户端本地执行后上报。
- 所有上报请求使用设备签名、时间戳和防重放。

### 5.5 Form Browser 本地化

当前 Agent 通过 `AGENT_FORM_BROWSER_URL` 调用服务端 form-browser。改为客户端 sidecar 后，需要反转任务流：

```text
Agent
  -> 生成表单任务和填写计划
  -> 通过事件/任务通道通知桌面端

Electron Main
  -> 调用本地 Form Browser
  -> 获取页面状态、截图、验证结果
  -> 将结果回传 Agent
```

Agent 仍部署在公网服务端，客户端只需要普通互联网即可完成任务下发和结果回传。form-browser 不依赖公司内网、VPN 或白名单网络。

需要注意：

- 登录态只保存在用户电脑。
- 浏览器状态和截图不上传服务器，除非用户明确操作。
- Agent 不能假设可以直接访问客户端的 8500 端口。
- 需要新增桌面任务通道、结果回调和超时处理。
- 如果目标表单自身只能在公司内网或 VPN 中访问，用户必须已经拥有对应网络权限；这不是桌面应用额外施加的限制。

### 5.6 JEV 替换 Laya

服务端 Agent 配置改为：

```text
AGENT_UNDERSTANDING_PROVIDER=jev
AGENT_UNDERSTANDING_PRIMARY=jev
AGENT_JEV_BASE_URL=https://...
AGENT_JEV_API_KEY=...
AGENT_JEV_MODEL=jev-1.13
```

需要完成：

- 移除 `services/intent` 的部署和启动。
- 删除 Laya 模型下载、torch 和模型同步流程。
- Agent 只保留 JEV 或规则/LLM 退化路径。
- JEV Key 只保存在服务端。
- 桌面端不能包含 JEV Key。

### 6.4 迁移

生产部署必须包含：

- Core 数据库迁移。
- Knowledge 数据库迁移。
- RAG 数据库迁移。
- 最新权限和删除相关迁移。

当前 Compose 的迁移列表需要补齐新增迁移，不能只依赖开发脚本手工执行。

### 6.5 网关

至少配置：

```text
/api/core/*      -> core-service
/api/knowledge/* -> knowledge-service
/api/rag/*       -> rag-service
/api/agent/*     -> agent-service
```

要求：

- HTTPS。
- SSE 禁用 buffering。
- Agent SSE 超时至少 480 秒。
- 上传限制与桌面端一致。
- 只暴露公网 API，不暴露内部 worker、OpenFGA、数据库和管理端口。
- 生产环境禁止 `/api/rag/internal/*`。

## 7. 桌面工程方案

### 7.1 目录结构

建议新增：

```text
apps/desktop/
  electron/
    main.ts
    preload.ts
    ipc/
    sidecars/
    auth/
    updater/
    config/
  resources/
    wechat-collector/
    form-browser/
  scripts/
  package.json
  electron-builder.yml
```

### 7.2 Electron 安全配置

- `contextIsolation: true`
- `nodeIntegration: false`
- `sandbox: true`
- 禁止 Renderer 直接打开任意本地文件
- 外部链接统一交给系统浏览器
- IPC 使用白名单
- 只允许生产 HTTPS API
- 配置 CSP
- 禁用不需要的 Electron 权限

### 7.3 Sidecar 管理

Sidecar Manager 需要支持：

- 随机 loopback 端口。
- 每次启动生成独立 token。
- 进程健康检查。
- 崩溃自动重启。
- 最多重启次数。
- 日志写入用户目录。
- 应用退出时优雅关闭。
- 单实例锁。
- 版本校验。

微信采集器要求：

- 使用本机微信数据目录权限。
- 不把数据库路径发送到服务端。
- 使用设备签名上报。
- 数据库路径和采集游标只保存在本机。

Form Browser 要求：

- 使用本地 Playwright/Chromium。
- 登录状态保存在本机。
- 页面截图和表单值默认不上传。
- 超时、失败和人工接管由 Main Process 统一管理。

## 9. 域名和 TLS

个人开发者的默认发布形态是：

```text
桌面客户端 -> 公网 HTTPS API
```

域名不是 Electron 打包的编译条件，但正式环境需要稳定的公网 HTTPS 地址。用户只需要普通互联网连接，不需要公司内网、VPN 或白名单网络。

推荐：

```text
app.example.com
api.example.com
update.example.com
```

以下方案仅适用于企业私有化部署，不是个人开发者首版的默认要求：

- 企业内网 DNS + VPN。
- 企业 CA 证书。
- 公网 IP + IP 证书，作为短期过渡。

不建议：

- 裸 HTTP 公网 API。
- 自签名证书分发正式客户端。
- 在客户端二进制中写死 IP。

## 10. 数据和安全

### 10.1 本机数据

存放在 `%APPDATA%/InfoAgent`：

```text
config.json
logs/
wechat-collector/
form-browser/
update/
```

密钥类数据放 OS Keychain/DPAPI，不放 JSON。

### 10.2 服务端数据

- 业务内容仍在 PostgreSQL、MinIO、Elasticsearch。
- Redis 负责任务和流。
- OpenFGA 负责权限。
- 不在桌面端保存完整业务数据副本。

### 10.3 安全要求

- TLS 强制。
- 设备签名。
- 时间戳和防重放。
- Token 不在日志中输出。
- JEV Key 不下发客户端。
- 采集数据库路径不上传。
- 表单页面截图默认本地保存并定期清理。

## 11. 测试与验收

### 11.1 服务端

- 所有后端启动健康检查通过。
- Agent worker 和 RAG worker 都运行。
- SSE 在 Nginx 后不断流。
- 数据库迁移可重复执行。
- OpenFGA 模型 ID 固定。
- JEV 调用成功，不再依赖 Laya。

### 11.2 桌面端

- 安装、升级、卸载正常。
- 启动时不弹出安全警告。
- 登录、刷新、退出正常。
- 断网时给出明确错误。
- WeChat Collector 自动启动。
- Form Browser 自动启动。
- 关闭应用后所有 sidecar 退出。
- 崩溃后能自动恢复。
- API 域名变更不需要重新打包。

### 11.3 安全验收

- Renderer 无法直接访问 Node API。
- 本地 sidecar 端口不对局域网开放。
- Refresh Token 在 Keychain。
- 日志不包含 Token 和微信数据库路径。
- 未签名更新包被拒绝。

## 14. 风险

| 风险 | 处理方式 |
| --- | --- |
| 服务端无法访问客户端 sidecar | 反转调用流，由客户端主动上报 |
| Cookie 在桌面环境异常 | 改 Keychain + Access Token |
| Python sidecar 打包困难 | 使用 PyInstaller/Nuitka，先做独立 EXE |
| Playwright 浏览器过大 | 独立安装 Chromium 或按需下载 |
| 无公网域名导致证书问题 | 发布前准备公共 HTTPS 域名和证书；企业内网域名仅作为可选方案 |
| 自动更新被劫持 | 签名校验、HTTPS、SHA-256 |
| 用户关闭应用后采集器残留 | Main Process 统一进程管理 |
| 服务端升级导致旧客户端不兼容 | API 版本化、最低客户端版本策略 |
