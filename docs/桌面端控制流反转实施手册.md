# 桌面端控制流反转实施手册

- 文档状态：评审修订版，待实施
- 编写日期：2026-10-07
- 修订日期：2026-10-07
- 适用范围：Knowledge、Agent、WeChat Collector、Form Browser、Electron 桌面端
- 目标：移除服务端到用户电脑 localhost 的反向调用，改为客户端主动连接服务端

## 1. 目标与结论

当前桌面化后存在两个方向错误：

```text
Knowledge -> 用户电脑 WeChat Collector
Agent     -> 用户电脑 Form Browser
```

服务端无法可靠访问用户电脑的 `127.0.0.1`、NAT 网络或本地 sidecar。

目标方向固定为：

```text
用户电脑客户端 -> 公网 HTTPS Knowledge / Agent 服务
服务端 -> 不主动连接用户电脑
```

控制流改为：

```text
服务端保存目标状态和命令
客户端主动拉取命令
客户端在本地执行
客户端回传状态和结果
服务端聚合最终状态
```

本方案不要求用户使用公司内网、VPN 或白名单网络。桌面应用默认连接公网 HTTPS 服务，只需要普通互联网。

### 1.1 实施原则

1. 复用已有的设备配对、设备密钥、HMAC 签名和防重放能力，不重新造一套认证。
2. Knowledge 和 Agent 各自管理自己的业务命令，不把两类业务塞进一张全局命令表。
3. 表单策略、知识检索、draft 生成和审批仍由 Agent 负责；桌面端只执行浏览器原子操作。
4. 第一版使用长轮询，不先引入 WebSocket。
5. 有副作用的任务不自动重放，失败后必须进入可审计状态。
6. Server 模式只作为 Web/开发和可信服务端 sidecar 的兼容模式，不作为桌面用户的业务回滚方案。

## 2. 模式边界

必须显式区分两种模式：

```text
COLLECTOR_MODE=desktop
COLLECTOR_MODE=server

FORM_BROWSER_MODE=desktop
FORM_BROWSER_MODE=server
```

### 2.1 Desktop 模式

- Collector 和 Form Browser 运行在用户电脑。
- 服务端不设置客户端 collector/form-browser URL。
- 所有客户端请求均由用户电脑主动发起。
- 不使用服务端共享 `X-Collector-Token` 代表桌面用户。
- 服务端启动时校验：桌面模式不能配置指向客户端的反向 URL。

### 2.2 Server 模式

- Collector 或 Form Browser 运行在服务端 sidecar。
- 只允许在该模式下使用服务端反向调用。
- 该模式只适用于可信的服务端部署，不适用于桌面用户电脑。
- Server 模式不能替代桌面模式的业务回滚。

### 2.3 模式选择

两种模式可以共存，但必须显式选择：

```text
桌面安装包默认：
COLLECTOR_MODE=desktop
FORM_BROWSER_MODE=desktop

旧 Web/服务端 sidecar：
COLLECTOR_MODE=server
FORM_BROWSER_MODE=server
```

任何模式都不得在运行时静默切换到另一种模式。配置错误应在启动或请求入口处失败，不能回退到 `127.0.0.1`。

## 3. 客户端到服务端的统一协议

### 3.1 命令协议

服务端下发命令统一使用以下结构。Knowledge 和 Agent 共享字段约定，但分别存储各自的业务命令。

```json
{
  "command_id": "uuid",
  "device_id": "device-uuid",
  "command_type": "wechat.collector.stop",
  "aggregate_type": "wechat_connector",
  "aggregate_id": "connector-uuid",
  "payload": {},
  "idempotency_key": "connector-uuid:config:12",
  "deadline": "2026-10-07T12:00:00Z",
  "attempt": 0,
  "created_at": "2026-10-07T11:00:00Z"
}
```

字段约束：

- `command_id` 全局唯一，用于去重和确认。
- `idempotency_key` 由业务状态和版本组成，不能用随机值代替。
- `deadline` 到期后命令进入 `expired`，不能继续执行。
- `payload` 的具体结构由 `command_type` 定义。

### 3.2 结果协议

客户端上报结果统一使用：

```json
{
  "command_id": "uuid",
  "device_id": "device-uuid",
  "status": "acknowledged",
  "result": {},
  "error_code": "",
  "error_message": "",
  "occurred_at": "2026-10-07T11:00:01Z"
}
```

### 3.3 命令状态

```text
pending
  -> delivered
  -> running
  -> acknowledged

pending / delivered / running
  -> failed
  -> expired
```

命令必须支持：

- 幂等键
- 过期时间
- 重试次数
- 设备绑定
- 用户和连接器归属校验
- 结果确认
- 失败原因
- 有副作用任务的禁止自动重放标记

### 3.4 客户端认证

继续使用 Knowledge 现有设备认证协议，不另起一套：

```text
X-Agent-Device-Key
X-Agent-Timestamp
X-Agent-Payload-Hash
X-Agent-Signature
```

签名内容：

```text
timestamp
method
request_path
payload_hash
```

服务端必须校验：

- 设备是否存在且未撤销
- 设备是否属于当前用户
- 设备是否绑定到当前 connector 或桌面任务
- 时间戳是否在允许窗口内
- 请求体 hash 是否匹配
- 签名是否匹配
- 请求路径和 method 是否一致
- 请求是否已经触发过防重放保护

### 3.5 认证归属

Knowledge 继续作为设备配对和 `agent_devices` 的权威服务。

为了不让 Agent 复制设备表或哈希逻辑，第一版约定：

```text
Agent 收到桌面端请求
  -> Agent 校验请求体和 payload_hash
  -> Agent 调用 Knowledge 内部设备校验接口
  -> Knowledge 使用现有设备密钥完成签名和防重放校验
  -> Agent 只接受 Knowledge 返回的有效设备身份
```

建议新增以下内部接口：

```text
POST /api/knowledge/v1/internal/devices/{device_id}/verify-request
```

请求使用服务间 token 保护，输入包括：

```text
X-Agent-Device-Key
X-Agent-Timestamp
X-Agent-Payload-Hash
X-Agent-Signature
original_method
original_path
```

返回：

```json
{
  "valid": true,
  "device_id": "device-uuid",
  "owner_user_id": "user-uuid",
  "connector_id": "connector-uuid",
  "expires_at": "2027-10-07T00:00:00Z"
}
```

Agent 可以缓存有效设备结果 30 秒，但不能缓存撤销结果过期；设备撤销后，下一次校验必须重新访问 Knowledge。

长期演进可以把设备身份提升到 Core，作为所有服务和桌面端共享的身份模块；第一阶段不要求移动现有表。

## 4. Knowledge 控制流反转

### 4.1 当前反向调用

当前 Knowledge 存在以下反向调用：

```go
s.WechatCollector().Stop(...)
s.WechatCollector().Conversations(...)
s.WechatCollector().Contacts(...)
s.WechatCollector().SaveConfig(...)
```

配置来源：

```text
KNOWLEDGE_WECHAT_COLLECTOR_URL
```

这些调用在 desktop 模式下必须移除或禁用。

### 4.2 复用现有目标状态

不新增 `wechat_desired_state`。现有表已经包含大部分目标状态：

```text
knowledge.wechat_collection_configs
  connector_account_id
  selected_conversations
  history_start_at
  enabled
  listen_mode
  config_version
  updated_at
```

需要补充和修改：

```text
desired_status VARCHAR(32)
  stopped
  running
  paused

config_version
  每次 Web 写入配置时递增
```

Web 操作只写 `wechat_collection_configs`：

```text
Web -> Knowledge: 保存配置并递增 config_version
Knowledge -> 客户端下一次 heartbeat 返回 desired_state
```

不直接调用用户电脑。

### 4.3 Knowledge 命令表

新增 Knowledge 自己的命令表，不创建全局 `desktop_commands`：

```text
knowledge.wechat_commands
  command_id UUID PRIMARY KEY
  connector_id UUID NOT NULL
  device_id UUID
  command_type VARCHAR(64)
  payload JSONB
  idempotency_key VARCHAR(255) UNIQUE
  status VARCHAR(32)
  attempt INTEGER
  deadline TIMESTAMPTZ
  delivered_at TIMESTAMPTZ
  completed_at TIMESTAMPTZ
  error_code VARCHAR(64)
  error_message TEXT
  created_at TIMESTAMPTZ
  updated_at TIMESTAMPTZ
```

第一版只支持以下命令：

```text
wechat.collector.start
wechat.collector.stop
wechat.collector.apply_config
```

`stop` 和 `apply_config` 都通过 `idempotency_key` 与 `config_version` 去重。

### 4.4 心跳返回目标状态和命令

扩展现有接口：

```text
POST /api/knowledge/v1/internal/devices/{device_id}/heartbeat
```

响应增加：

```json
{
  "desired_state": {
    "desired_status": "stopped",
    "enabled": false,
    "selected_conversations": ["chat-a"],
    "listen_mode": "whitelist",
    "history_start_at": "2026-10-01T00:00:00Z",
    "config_version": 12
  },
  "commands": []
}
```

第一版不使用 WebSocket，直接由 heartbeat 返回 state 和命令。

### 4.5 Collector 本地执行

Collector 收到 heartbeat 后：

```text
读取 desired_state
对比本地 config_version
应用配置
执行 start/stop/apply_config
上报状态和 command ack
```

新增或扩展以下设备接口，接口仍由 Knowledge 设备认证保护：

```text
POST /api/knowledge/v1/internal/devices/{device_id}/wechat/state
POST /api/knowledge/v1/internal/devices/{device_id}/wechat/snapshot
POST /api/knowledge/v1/internal/devices/{device_id}/commands/{command_id}/ack
```

### 4.6 会话和联系人快照

`Conversations` 和 `Contacts` 不再由 Knowledge 反向调用采集器。

新增快照表：

```text
knowledge.wechat_snapshots
  connector_id UUID
  snapshot_type VARCHAR(32)
  device_id UUID
  version BIGINT
  items JSONB
  captured_at TIMESTAMPTZ
  expires_at TIMESTAMPTZ
  PRIMARY KEY (connector_id, snapshot_type)
```

`snapshot_type` 至少支持：

```text
conversations
contacts
```

采集器定期上报：

```json
{
  "connector_id": "connector-uuid",
  "snapshot_type": "conversations",
  "version": 7,
  "items": [],
  "captured_at": "2026-10-07T11:00:00Z"
}
```

Knowledge 保存快照，Web UI 查询 Knowledge 中的最新快照。快照过期时可以显示缓存数据，但必须显示 `captured_at` 和过期状态。

### 4.7 状态查询

`WechatStatus` 只读以下服务端状态：

```text
wechat_collection_configs
wechat_collector_runtime
wechat_snapshots
```

不调用用户电脑：

```text
Knowledge -> collector HTTP
```

### 4.8 必须清理的反向调用点

至少检查并修改以下位置：

```text
StopWechat
WechatConversations
DiscoverByType 中的 WeChat 分支
DiscoverContacts 中的 WeChat 分支
SaveWechatConfig
RevokeConnector 中的 best-effort Stop
HeartbeatDevice
WechatBootstrapForDevice
```

`WechatStatus` 保持只读，但读取来源改为 configuration、runtime 和 snapshots。

## 5. Agent 控制流反转

### 5.1 当前反向调用

当前 Agent 通过：

```text
AGENT_FORM_BROWSER_URL
```

直接访问 Form Browser。

桌面模式下不能直接把旧的 `FormBrowserClient` 指向客户端，因为服务端无法访问客户端 `127.0.0.1`。
但也不要把整个 `form.preview` 和 draft 生成逻辑搬到 Electron。

### 5.2 正确的职责边界

Agent 继续负责：

- `form.preview` 的计划和参数校验
- 知识检索和缺失字段补齐
- draft 构建
- 审批绑定
- `form.apply` 的确认和结果收敛

桌面端只负责浏览器原子操作：

```text
open
read_grid
read_form
clear_range
write_grid
fill_form
submit_form
screenshot
send_input
```

这样现有 `form.preview`、`form.apply` 及其测试逻辑可以继续保留。

### 5.3 Agent 桌面任务表

新增 Agent 自己的任务表，不使用全局命令表。

`desktop_task_id` 和 `agent_task_id` 必须区分：

```text
agent.desktop_tasks
  desktop_task_id UUID PRIMARY KEY
  agent_task_id UUID
  agent_step_id UUID
  device_id UUID
  operation VARCHAR(32)
  request_payload JSONB
  status VARCHAR(32)
  result JSONB
  result_hash CHAR(64)
  error_code VARCHAR(64)
  error_message TEXT
  attempt INTEGER
  lease_owner VARCHAR(128)
  lease_expires_at TIMESTAMPTZ
  expires_at TIMESTAMPTZ
  delivered_at TIMESTAMPTZ
  started_at TIMESTAMPTZ
  completed_at TIMESTAMPTZ
  side_effect_state VARCHAR(32)
  created_at TIMESTAMPTZ
  updated_at TIMESTAMPTZ
```

`operation` 对应浏览器原子操作。`request_payload` 中保存 `session_id`、URL、selector、values 等操作参数，不保存微信数据库路径或浏览器密钥。

### 5.4 DesktopFormBrowserClient

新增一个适配器，保持现有 `FormBrowserClient` 的方法签名：

```text
DesktopFormBrowserClient
  -> create_session
  -> close_session
  -> open
  -> read_grid
  -> write_grid
  -> clear_range
  -> read_form
  -> fill_form
  -> submit_form
  -> screenshot
  -> send_input
```

每个方法：

```text
创建 agent.desktop_tasks
等待桌面端拉取
等待结果回传
将结果转换成现有 FormBrowserClient 返回格式
```

第一版可以使用服务端短等待或长轮询。超时后：

- 只读操作可以重新入队。
- `submit_form` 等有副作用操作不能自动重放。
- 有副作用操作超时进入 `needs_review` 或 `failed`，并要求用户确认实际结果。

### 5.5 Form Preview 流程

```text
Agent 生成 form.preview
-> 通过 DesktopFormBrowserClient 向原设备请求 open/read
-> 本地 Form Browser 执行只读操作
-> Agent 读取结果并检索知识、构建 draft
-> Agent 生成审批
```

如果本地浏览器需要登录：

```text
登录是只读阶段
-> 可以进入 login_required
-> 用户完成登录
-> 重新执行同一个 preview 操作
```

### 5.6 Form Apply 流程

审批通过后：

```text
Agent 生成 form.apply task
-> 下发到原桌面设备
-> Electron Main 调用本地 Form Browser
-> 本地执行 clear/write/fill/submit
-> 上传 apply result
-> Agent 收敛任务
```

Apply 任务必须绑定：

- 原 `device_id`
- 原 `agent_step_id`
- 原 draft 或参数 hash
- 原浏览器 session
- 幂等键

不能在另一台设备或另一个浏览器 session 上自动重放。

### 5.7 Takeover 和登录流程

当前 `/tasks/{task_id}/takeover` 直接调用服务端 Form Browser 的截图和输入接口。桌面化后该路径失效，必须显式处理。

第一版建议：

```text
form browser 返回 login_required
-> Agent 将任务标记为 waiting_login
-> Electron 在本地提示用户完成登录
-> 用户完成登录后，桌面端主动重新提交同一 desktop task
-> Agent 恢复任务
```

完整 takeover 方案作为后续增强：

```text
Agent -> desktop task: takeover.screenshot
Agent -> desktop task: takeover.input
Desktop -> result: screenshot/task state
```

无论采用哪种方案，Renderer 不能直接访问本地 `localhost:8500`。

### 5.8 禁止访问的地址

桌面模式下以下配置必须为空或无效：

```text
AGENT_FORM_BROWSER_URL=http://127.0.0.1:8500
```

服务端 Agent 不能假设自己能访问客户端的 8500 端口。

### 5.9 桌面任务接口

Agent 负责以下公网桌面接口：

```text
GET  /api/agent/v1/desktop/tasks?device_id=...
POST /api/agent/v1/desktop/tasks/{desktop_task_id}/claim
POST /api/agent/v1/desktop/tasks/{desktop_task_id}/result
POST /api/agent/v1/desktop/tasks/{desktop_task_id}/heartbeat
```

第一版使用 HTTPS long-poll。SSE 作为后续优化项。

这些接口的认证流程复用第 3.5 节的 Knowledge 设备校验，不复制设备表。

## 6. Electron Main Process 职责

Electron Main Process 统一管理：

```text
WeChat Collector sidecar
Form Browser sidecar
本地浏览器 session
设备密钥和 refresh token
```

职责包括：

- 启动和停止 sidecar
- 监控进程健康状态
- 分配本地 loopback 端口
- 通过 IPC 向 Renderer 暴露状态
- 拉取 Knowledge 命令
- 拉取 Agent 桌面任务
- 执行本地浏览器原子操作
- 上传结果和状态
- 处理断线重连和离线队列
- 退出时清理 sidecar
- 保存设备密钥和 refresh token

Renderer 不应该直接访问：

```text
localhost:8091
localhost:8500
```

Renderer 只访问 Electron IPC，由 Main Process 统一代理。

## 7. 数据流

### 7.1 WeChat

```text
Electron Main
  -> WeChat Collector
       -> Knowledge heartbeat
       -> Knowledge state/snapshot/ack
       -> Knowledge messages/attachments/cursors
```

### 7.2 Form

```text
Agent
  -> agent.desktop_tasks
Electron Main
  -> local Form Browser atomic operations
  -> agent.desktop_tasks result
Agent
  -> approval / completion
```

### 7.3 网络方向

```text
用户电脑客户端 -> 公网 HTTPS 服务端
用户电脑客户端 -> 目标网站
```

禁止：

```text
服务端 -> 用户电脑 127.0.0.1
服务端 -> 用户电脑局域网地址
服务端 -> 用户 VPN 内网地址
```

## 8. 兼容和迁移

### 8.1 保留 Server 模式

原有服务端 sidecar 模式可以保留，但必须显式开启：

```text
COLLECTOR_MODE=server
FORM_BROWSER_MODE=server
```

桌面模式：

```text
COLLECTOR_MODE=desktop
FORM_BROWSER_MODE=desktop
```

Server 模式只用于可信服务端 sidecar 和开发调试，不用于桌面用户业务回滚。

### 8.2 移除桌面模式反向配置

桌面模式下不需要：

```text
KNOWLEDGE_WECHAT_COLLECTOR_URL
AGENT_FORM_BROWSER_URL
VITE_WECHAT_AGENT_URL
```

如果保留这些变量，只能作为服务端 sidecar 的开发或兼容配置。

### 8.3 历史状态迁移

- 将现有 `wechat_collection_configs` 作为目标配置的唯一来源。
- 为 `wechat_collection_configs` 补充 `desired_status`。
- 将 Web 配置写入现有配置表并递增 `config_version`。
- 将当前 `wechat_collector_runtime.status` 作为当前运行状态。
- 将采集器上报的会话和联系人写入 `wechat_snapshots`。
- 将已有表单任务迁移或重新绑定到 `agent.desktop_tasks`。
- 未确认的旧反向调用记录标记为服务端模式历史，不参与桌面任务重放。

### 8.4 迁移规则

- 迁移必须 additive，不删除旧状态字段。
- 命令和快照表必须有唯一键、索引和清理策略。
- `agent.desktop_tasks` 不建立跨 schema 的强外键到 `knowledge.agent_devices`，设备有效性通过认证接口校验。
- 迁移不得修改或删除已有的用户表单和待办数据。

## 9. 实施顺序

### Phase 0：方案冻结和兼容基线

- 确认 Knowledge 作为第一阶段设备身份权威服务。
- 确认 Agent 通过 Knowledge 校验桌面设备。
- 确认使用长轮询。
- 确认表单原子操作边界。
- 确认 takeover 第一版采用本地登录提示方案。
- 保留 Server 模式用于 Web/开发，不用于桌面回滚。

### Phase 1：协议和数据库

- 定义 command/result JSON。
- 为 `wechat_collection_configs` 增加 `desired_status`。
- 增加 `knowledge.wechat_commands`。
- 增加 `knowledge.wechat_snapshots`。
- 增加 `agent.desktop_tasks`。
- 增加设备请求校验接口。
- 增加命令 ack、幂等和过期查询。

### Phase 2：Knowledge 反转

- Heartbeat 返回 desired state 和 commands。
- Collector 本地执行命令。
- Conversations/Contacts 改为快照上报。
- Stop/SaveConfig 改为写 desired state。

## 10. 测试和验收

### 10.1 Knowledge

- Web 点击停止后，只更新 desired state 和命令。
- Collector 拉取后本地停止并上报。
- Knowledge 不访问任何客户端 localhost。
- 采集器离线时配置保留，上线后补齐。
- 重复 heartbeat 不重复执行同一配置版本。
- 会话和联系人来自 Knowledge 快照，不依赖采集器在线。

### 10.2 Agent

- Agent 对同一 device 下发 open/read/write/submit 原子任务。
- Agent 生成 preview task，不调用客户端 8500。
- Agent 仍在服务端完成 draft 和审批。
- 预览、审批、apply 状态能够收敛。
- 重复 callback 不会重复填写或重复提交。
- 任务超时后进入 expired，有副作用任务不会自动重放。
- 断开桌面端后重新连接可以恢复未完成的只读任务。

### 10.3 安全和隔离

- 设备签名、时间戳和 payload hash 校验通过。
- 设备撤销后旧命令无法继续使用。
- 不同用户、设备和连接器不能互相读取命令。
- Token、Cookie、微信数据库路径不出现在日志。
- sidecar 只绑定 `127.0.0.1`。
- Renderer 不能直接访问 sidecar 端口。

### 10.4 网络

- 普通家庭网络、移动网络和办公网络均可使用。
- 用户不需要公司内网或 VPN。
- 只有目标网站自身要求内网/VPN 时，用户的网络环境才成为限制。
- 服务端不接收客户端入站连接。

### 10.5 Takeover

- 本地登录缺失时任务进入明确的 `waiting_login`。
- 用户完成本地登录后可以恢复原任务。
- 不把用户浏览器登录态上传到服务端。
- 完整 takeover 上线前，不能宣称现有远端 takeover 路径可用。

## 11. 回滚策略

- 新表采用 additive migration，不删除旧状态字段。
- 命令和任务状态支持幂等确认，不依赖客户端重放。
- 桌面端发布前先完成灰度设备验证。
- 桌面功能异常时关闭对应桌面能力或回滚客户端版本。

以下不是桌面业务的回滚方案：

```text
FORM_BROWSER_MODE=server
COLLECTOR_MODE=server
```

它们只适用于 Web/开发和可信服务端 sidecar。服务端 sidecar 无法读取用户电脑上的微信数据库和浏览器登录态。

## 12. 风险

| 风险 | 处理方式 |
| --- | --- |
| 客户端离线导致命令长期 pending | 增加 TTL、重试和过期状态 |
| 命令重复执行 | 使用 command_id/idempotency_key |
| 设备被撤销后继续执行 | 每次拉取和上报校验设备状态 |
| 桌面 sidecar 崩溃 | Main Process 自动重启并保留重启原因 |
| 浏览器或表单提交产生副作用 | Preview/Apply 分阶段审批，Submit 不自动重试 |
| 服务端仍配置反向 URL | 启动时按模式校验空值 |
| 多设备绑定冲突 | 命令和设备 ID、连接器 ID、用户 ID 绑定 |
| 快照过期 | 记录 captured_at/version，UI 显示过期状态 |
| Agent 复制设备认证 | 只调用 Knowledge 设备校验接口，不复制表 |
| 表单 draft 逻辑漂移 | draft 始终留在 Agent，桌面端只执行原子操作 |
| takeover 登录态不同步 | 第一版本地登录提示，后续再做完整 takeover |
